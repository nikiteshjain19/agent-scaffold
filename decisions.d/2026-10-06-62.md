# D-62 — 2026-10-06 — The `pr-reviewer` skill reviews what would land, with nothing the author wrote

- **Decision:** The `pr-reviewer` skill changes in eight ways.
  1. **Independence covers what the reviewer reads on the host**, not only what its invocation
     carries. It never reads a pull request comment that opens with `VERDICT`,
     `REPAIRED BY THE MERGE LOOP` or `MERGE-LOOP REVIEW RECORD`. It reads ticket comments only for
     scope changes, never takes a comment's claim about the diff as evidence, and records in
     `INDEPENDENCE` any such text it read anyway. The skill runs as a freshly dispatched agent,
     "identifiers only" admits fixed instruction lines that describe no change, and BASE is read
     from the host before its first use.
  2. **Pre-merge check 4 tests the merged tree.** When BASE has moved, the reviewer runs
     `git merge --no-commit --no-ff origin/<BASE>` in its detached worktree, never pushed, and runs
     the pre-PR gate on the result. A conflict or a red gate fails check 4. `CLAUDE.md` §6
     pre-merge check 4 now says the same: test the merge on a local, detached copy of the PR head,
     and merge into the PR branch itself only to resolve a conflict.
  3. **Decision freshness reads what BASE gained**, not what is dated after the branch point. The
     reviewer lists the entries added, modified or deleted under `decisions.d/` between the merge
     base and `origin/<BASE>`, with `git diff --name-only --diff-filter=AMD`, and reads each from
     `origin/<BASE>`. An entry the pull request itself adds is judged under
     check 1. `CLAUDE.md` §6 pre-merge check 2 now reads "every decision entry the default branch
     gained since this PR's branch point, whatever its date".
  4. **`reject` is narrowed to a check-1 defect the diff can repair**, as `CLAUDE.md` §6 defines
     repairable. A weakened test, a stale record, a contradicted decision, a duplicate and a
     cancelled ticket now return `escalate`.
  5. **The checks run without credentials.** Every §3 command, and check 4's run on the merged
     tree, runs in an environment that removes the host CLI's token and stored login, git's
     credential helpers and the SSH agent. A command that cannot run there escalates. The skill
     says plainly that this environment is not a sandbox.
  6. **Two stops fix the verdict and still review.** With no green signal declared, and on an
     inline invocation, the verdict is fixed at `escalate` and every check and condition is still
     reported. An inline invocation reads `not established — inline invocation`. Every other stop
     still ends the run.
  7. **Check 6 reads a declared out-of-band step as `unevaluable`**, and an undeclared one as
     `fail`. It passes only when the pull request needs nothing outside the repository.
  8. **The verdict comment is the independent verdict the `CLAUDE.md` §6 review record cites**,
     never that record itself. The `pr-merge-loop` skill's `MERGE-LOOP REVIEW RECORD` is the
     record. Every verdict posts, an early `escalate` included.
- **Context:** #62, from two audits of the `pr-reviewer` skill on 2026-10-06. The owner approved
  the issue's plan ("I'm good with all the changes. Let's go ahead.") and the second audit's
  additions ("apply 14 to 21 to sixty-two as written"). Item 8 is the owner's ruling on #10 item 6,
  moved into #62 on 2026-10-06.

  **Why independence reaches host reads.** The excluded-items list governed only what the
  invocation carried, while GATHER told the reviewer to read every ticket comment, and the host
  holds exactly the builder's account, the earlier verdicts and the repair records that list
  excludes. PR #59's round-2 verdict shows the gap: its `INDEPENDENCE` field reads that the earlier
  verdict and the repair record were read from the host as evidence. A reviewer that reads them
  there is independent in name only. Ticket comments stay readable for scope, because check 5
  needs a cancellation or a descope, and nothing else in a comment is evidence about the diff.

  **Why check 4 tests the merged tree.** A pull request green on its own head can break once
  merged with a BASE that moved, and the old check only asked whether BASE moved. The merge-loop's
  auto lane relies on the reviewer for exactly this check, so a green head was enough to
  auto-merge a broken result. A local, detached, never-pushed merge tests what would land without
  writing to the branch, which the reviewer may never do. D-13's reasoning, that check 4 makes the
  merging flow re-check staleness itself so the ruleset need not require up-to-date branches, still
  holds and is made stronger, so this entry writes no relation to D-13.

  **Why freshness reads what BASE gained.** "Dated after the branch point" compares a commit
  timestamp with a filename date at day granularity, and fifteen entries share 2026-10-05, so a
  same-day entry merged after the branch point was missed. The set of entries BASE gained since the
  merge base is exact, whatever the dates say.

  **Why `reject` is narrowed.** `reject` overlapped the escalation conditions: a weakened test and
  a contradicted decision both fire a condition that `CLAUDE.md` §6 lists as never repairable, and
  a cancelled ticket or a duplicate is a scope decision. A caller that sends every `reject` to a
  repairer would then ask it to decide scope. Keeping `reject` for the repairable check-1 defects
  makes the verdict say what the next actor can do.

  **Why the checks run without credentials.** §3 runs the pull request's own code in a shell that
  held the host CLI's login, and that CLI can merge and push. So a buggy or hostile pull request
  could merge itself from inside its test run. Unsetting `GH_TOKEN` is not enough, because `gh`
  can keep its token in the system keyring; an empty `GH_CONFIG_DIR` hides it, and an empty global
  git config removes the credential helper. A real sandbox would also stop the checks reading the
  user's files, and is out of scope; the skill says so instead of implying more protection than it
  gives.

  **Why two stops still review.** With no green signal, or on an inline invocation, the old text
  returned `escalate` and nothing else, so a user asking "is this safe to merge" got no review at
  all. The verdict cannot be `approve` in either case, but the findings are still true and still
  useful to the human who decides. The stops that still end the run are the ones where a review
  would be wrong to give (an authored branch, a self-spawned review, an excluded item) or has
  nothing to review against (no `PROJECT.md`, no merge gate).

  **Why check 6 reads a declared step as `unevaluable`.** The old check asked the reviewer to
  confirm a live system it cannot reach. `CLAUDE.md` §6 pre-merge check 6 is unchanged; this is its
  fail-closed reading for an agent with no access to the live system, and nothing in the auto lane
  performs the step, so a declared step sends the pull request to a human.

  **Why the verdict comment is not the review record.** Both skills claimed their comment was the
  §6 review record, and §6 says one comment, posted by the agent that ran the review. The owner
  ruled that the merge loop's record is the §6 record and that it cites the reviewer's comment as
  the independent verdict. #63 writes the `pr-merge-loop` half.

  **No relation.** Condition 6 now reports independence alone, and a comment its code contradicts
  now fails check 1. Both agree with D-5, whose field names and layout are unchanged, and with
  D-11, which already made a check-1 finding blocking and never advisory. D-13 still binds as
  above. This entry writes neither `Supersedes` nor `Corrects`.
