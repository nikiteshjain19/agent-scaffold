# D-51 — 2026-10-05 — `npm run lint` fails on a duplicate decision id, so the green signal enforces §7

- **Decision:** This repository enforces `CLAUDE.md` §7's rule that two decision entries never
  claim one id. `.github/scripts/check-decision-ids.mjs` reads the first line of every `*.md` file
  directly in `decisions.d/`. It takes the entry's own id only from the heading's opening
  `# D-<id>`, followed by a space: the capture of `^# (D-[0-9]+[a-z]?)` plus that space. It fails
  when two files claim one id, or when a file's first line yields no own id. `package.json`'s
  `scripts.lint` runs it after `markdownlint-cli2`, so the required `Markdown lint` check fails on
  either problem.
- **Context:** #51. §7 says two entries must never claim one id, and leaves enforcement to the
  project: "Enforce it however the project likes". Until this change, nothing here enforced it. No
  document, skill, script or CI job checked `decisions.d/`. Issues copied an ad-hoc shell check into
  their Verification sections instead, and that check was wrong. It collected every id on each
  heading line, and D-36's heading mentions D-13 ("so D-13's record of a waiting window is stale"),
  so on a clean `main` it reported `D-13` as a duplicate. The lanes for #45 and #46 each had to
  explain that false positive away in their PR bodies (PR #49, PR #50). A mention is not a claim,
  and since D-46 a heading may also carry a `scaffold D-N` or `private D-N` citation. So the check
  reads only the id that opens the heading, followed by a space.

  **The owner's choice.** Asked whether the corrected command should live in (a) `PROJECT.md`, (b)
  the `issue-writer` skill, or (c) a CI check that fails the PR on a duplicate id, the owner
  answered on 2026-10-05: "let's go with C a CI check". A command in a document only helps an agent
  who copies it correctly, which is how the broken one spread. A CI check cannot be skipped, and it
  joins the green signal mergers already trust.

  **Where the check runs.** Three placements were weighed:
  1. **A script that `npm run lint` runs after `markdownlint-cli2` — chosen.** The required
     `Markdown lint` check fails, so it blocks a merge. The local pre-PR gate runs it unchanged,
     as `npm ci && npm run lint`. Only `package.json` and one new script change.
  2. **A new step in the `Markdown lint` job.** It would also block a merge, but the local pre-PR
     gate would not run it unless `PROJECT.md` quoted a second command. A second quoted command is
     exactly how the broken check spread.
  3. **A separate job.** It would not block a merge. The ruleset `main — merge gate` requires only
     `Markdown lint`, and only the owner can add a second required check (D-13).

  The chosen placement keeps one command, `npm run lint`, as the check everywhere, so no issue needs
  to copy a duplicate-id command into its Verification section again.

  **Why the script sits under `.github/`.** The `.github/**` entry on the risk list already covers
  it. A change to the code that decides the green signal must reach a human, and placing it there
  needs no new risk-list entry. It also stays at the repository root with the rest of the lint
  tooling, outside the plugin directory D-48 created.

  **Why `Corrects` D-3, not `Supersedes`.** D-3 still binds: the green signal is still the
  `Markdown lint` job, on pinned tooling, running `npm ci` and then `npm run lint`. What that job
  checks has grown, so a reader must read both entries.

  **How the check was proved.** #51's Verification seeded a duplicate, a heading with no own id, and
  a heading that mentions other ids, and recorded each result in the pull request. The project has
  no test runner, so those seeded runs are the failure-branch evidence.
- **Corrects:** D-3.
- **Affects:** `package.json` (`scripts.lint`); `.github/scripts/check-decision-ids.mjs`;
  `PROJECT.md`, "Build / lint / test commands" and "Green signal"; D-3
  (`decisions.d/2026-10-05-3.md`); #47; #48; #51.
