# D-7 — 2026-10-06 — A relayed answer names its pull request and head, and only the user's own words approve

- **Decision:** The `cycle-manager` skill's C5 brief gains one line after the user's answer:
  `The answer was given for: pull request <N>, head commit <SHA, or none>`. The manager fills it from
  the digest entry the user answered, whose head is the verdict's `HEAD`, and writes `none` for the
  head when the user gave no answer. The DIGEST phase names that head on each entry, and the MERGE
  phase carries it. The `pr-merge-loop` skill gains an A RELAYED ANSWER section, which SINGLE-PR
  MODE step 8, the DIGEST and the RULES point to. In the auto lane the merger needs no answer and
  never waits for one: `not yet approved` holds nothing, and only an answer that declines the PR
  holds it. In the escalate lane the merger accepts a relayed answer as approval only when four
  checks pass, in order: the answer is the user's own words, it names this PR, it names a head
  that equals the PR's current head read from the host, and the words approve this PR. A failure
  of any of the first three is a refusal. The merger states it in one plain sentence before the
  card, builds the card on the current head, and queues its merge question. `not yet approved` is
  no answer and not a refusal. C1, C2, C3, C4, C6, C7 and C8 are unchanged, and so are C6's four
  field names and what each one counts.
- **Context:** #7, from an audit on 2026-09-18. The `cycle-manager` skill presents one digest and
  carries each answer into a merger, but the `pr-merge-loop` skill said answer handling "stays
  where the question was asked", and no section of it read an answer that arrived from somewhere
  else. In the escalate lane that meant the user's go-ahead from the manager's digest was ignored:
  the merger built its own card, queued the same question, and the manager could ask it again every
  cycle until the cap. In the auto lane the manager's `not yet approved` read as a hold on a pull
  request the gate had already cleared. SINGLE-PR MODE (D-6) already chose the auto lane from the
  classification and the verdict alone, but nothing said the answer line was irrelevant there, and
  the DIGEST sentence contradicted it.

  **Why C5 changes, and not only the merger.** The issue requires a relayed answer to name the
  pull request and the head it was given for, because `CLAUDE.md` §6 approval rule 4 expires an
  approval when the diff changes. C5 carried the verdict's `HEAD`, which says what the reviewer
  read, not what the user saw. Today the two are the same commit, since the manager presents each
  entry from its verdict and SINGLE-PR MODE voids a verdict whose `HEAD` has moved. They need not
  stay the same: #20 will carry a merger's question into a later cycle's digest. Naming the
  answer's own head lets the merger check approval rule 4 against the answer itself, rather than
  inferring it from a different field. A separate line keeps the user's words untouched inside
  their quotation marks.

  **Why the merger checks the words, and what it cannot check.** Approval rule 1 says only the
  user's own words approve, and the manager's skill already forbade paraphrase. But a rule on the
  sender alone fails silently: a merger that receives "the user approved #12" has no instruction
  telling it that this is not approval. The merger can recognise words written about the user
  rather than by the user, and it refuses whenever it cannot tell, which is the fail-closed bias
  the skill already applies to every other input. It cannot prove the words were typed by the user;
  nothing in a relay can. The check catches the summary a careless relay produces, which is the
  failure the issue names.

  **Why a refusal still queues the question.** Refusing and stopping would leave the pull request
  with no path to the user's actual words. Building the card and queuing its merge question sends
  the decision back to the user in the ordinary shape, so the next answer can be relayed correctly.
  The `CYCLE-MERGE-RESULT` block already counts that question in `queued`, so C6 needs no change.

  **Why a decline holds an auto-lane pull request without the checks.** The checks exist to stop a
  relay manufacturing an approval. Holding a pull request is the fail-closed direction, so an
  unverified decline costs one pull request staying open, while ignoring a real one would merge
  something the user said to skip.

  **What this leaves to #20.** The manager's MERGE phase still runs only for the pull requests its
  digest covered, so an approved pull request with no question does not yet reach a merger. #20
  sends every finished pull request to MERGE, carries a question across cycles, and handles a hard
  stop. This entry defines only what the merger does with an answer once one arrives.

  **No relation.** D-6 gave C5 its single-pull-request wording, and that wording still binds
  unchanged. This entry adds a line beside it, so D-6 is neither superseded nor corrected.

  **Why this is a decision.** The `cycle-manager` skill says its contracts are frozen and that
  changing one is a decision (`CLAUDE.md` §7). This entry is the record that the owner approves the
  C5 change knowingly, with the pull request that makes it.
- **Affects:** the `cycle-manager` skill (the relay rule's merger bullet, C5 and its frozen

  (SINGLE-PR MODE step 8, the new A RELAYED ANSWER section in ESCALATE LANE, the DIGEST's answer
  handling paragraph, and a RULES bullet); #7; #20, the cycle-manager half of this defect.
