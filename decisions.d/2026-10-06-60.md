# D-60 — 2026-10-06 — A `feature-plan` plan lands through its own unit, records its decisions, orders by links, and declares complete footprints

- **Decision:** The `feature-plan` skill changes in six ways that shape how future plans are
  written and scheduled.
  1. **The plan reaches the default branch through its own unit.** The skill writes
     `docs/plans/<slug>.md` to the working tree, leaves it uncommitted, and presents it. Every
     approved plan whose units go to the `issue-writer` skill carries a "Commit this plan" unit in
     wave 0, as that wave's only unit or beside a wave-0 layout unit. Every other unit is blocked
     by it. The `issue-writer` skill files it like any other unit, so the plan lands through an
     issue and a pull request. The skill itself still never commits and never creates a branch.
  2. **Plan decisions reach the decision log.** The "Commit this plan" unit also writes a decision
     entry, `decisions.d/<date>-<that unit's issue id>.md`, recording the chosen approach, the
     rejected alternatives, and the frozen contracts or a pointer to the plan's Contracts section.
     Its footprint is the plan file and that entry. A contract change after approval is a new entry
     that `Supersedes` or `Corrects` the plan's entry and names the earlier file in its footprint.
  3. **A wave is not a barrier.** A unit starts once its own blocked-by units have merged, and
     does not wait for the rest of its predecessor wave. The wave number orders the plan and groups
     disjoint units. A plan-wave number is compared only within one plan file, and it never holds
     an issue back.
  4. **Every ordering is a "blocked by" link.** Each ordering the plan depends on is an entry in
     the Waves table's blocked-by column, wave 0 included, so a unit waits only for what its row
     names.
  5. **A decision reversal is a question, not a unit.** A plan that would reverse a logged decision
     asks the reversal as an explicit question at the approval gate. Units that depend on it are
     planned against the user's answer, never against an assumed one.
  6. **Unit footprints are complete.** A unit's footprint names every document the unit makes
     false, by document and section, and every earlier decision file a `Supersedes` or `Corrects`
     back-reference edits. Disjointness is tested on that complete list.
- **Context:** #60, from two reviews of the `feature-plan` skill on 2026-10-06. The owner approved
  filing the first review ("lets create a ticket with whatever seems important and needs to be
  changed") and the second audit's additions ("I'm good with all the changes. Let's go ahead.").

  **Why a "Commit this plan" unit.** The skill wrote its plan to `docs/plans/<slug>.md` and its
  HARD RULES forbade creating a branch. The plan was then either lost with the session or committed
  straight to the default branch, which `CLAUDE.md` §3 forbids. Letting the skill open its own
  branch and pull request was the alternative, and it was rejected: it would make a design agent
  also an implementing agent, and it would land the plan outside the issue flow every other change
  uses. A unit filed like any other keeps one path to the default branch, and blocking every other
  unit by it means no implementer works from a plan that is not yet on the default branch.

  **Why the plan writes a decision entry.** The plan's approved design and frozen contracts are
  decisions in the `CLAUDE.md` §7 sense: they change how future issues are implemented. Left only
  in the plan file, they were invisible to the decision-freshness check, which reads the log, and a
  later contract change had no relation to mark what it switched off. An entry per plan, written by
  the unit that lands the plan, puts both in the log at the same moment.

  **Why waves are not barriers, and why every ordering is a link.** The skill numbered waves, and
  a reader could take "wave 2" to mean "after all of wave 1", which holds a unit back for work it
  does not depend on. The `issue-loop` skill dispatches by blocked-by relations and by plan-scoped
  wave order (scaffold D-64), so a plan that orders only by wave number tells the loop less than it
  needs. Writing every ordering as a link makes the barrier rule checkable: a unit waits for exactly
  what its row names.

  **Why a reversal is a question.** The skill told a plan to propose a reversal "as its first
  unit". Reversing a decision is the user's call, and a unit that performs it would let an
  implementer reverse a decision because a plan scheduled it. Asking at the approval gate puts the
  call where the user already decides.

  **Why complete footprints.** A unit that makes a document false must repair it in the same pull
  request (`CLAUDE.md` §5 rule 6), and an entry that writes a back-reference edits the earlier
  entry's file (`CLAUDE.md` §7). Both are files the unit's branch changes. A footprint that omits
  them understates the unit, so two units the plan shows as disjoint can still collide.

  **Provenance.** `private D-19` introduced the `feature-plan` skill and its `docs/plans/`
  location. That entry is not in this repository's log, so this entry writes neither `Supersedes`
  nor `Corrects`.
