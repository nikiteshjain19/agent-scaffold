# D-65 — 2026-10-06 — The `project-audit` skill surveys what the code contains, with no side effects

- **Decision:** The `project-audit` skill changes in eight ways.
  - **Applicability comes from the code.** Whether a step applies is decided from the code and the
    dependency manifests, never from `PROJECT.md` alone. A step is skipped only when a named search
    finds no such integration, and an integration the code uses but `PROJECT.md` omits is a
    finding. With no `PROJECT.md`, every input is resolved from the repository and labelled
    inferred.
  - **Read-only means introspection only.** The skill's introduction carries this rule, verbatim:
    "**Read-only means introspection only:** schema, grants, configuration, logs and advisors.
    Send no request that writes data, sends a message, moves money, calls a paid API or changes
    third-party state. Never load-test. Run the test suite only when it needs no live service and
    no credential. Otherwise record "not run", and why."
  - **Live-system rules sit beside it.** Every live query runs inside a read-only transaction; a
    metadata-only tool call needs none; a tool offering neither runs no query, and the check is
    recorded as not verified. No step calls a tool that applies a migration, deploys, or creates,
    resets or merges a branch. `EXPLAIN ANALYZE` runs only on a `SELECT`. Live checks read
    metadata and aggregate counts only, never the values in a row of a table that holds user data,
    and any value that appears anyway is redacted.
  - **The suite run reads its configuration first.** Before any run, the skill reads the runner's
    configuration, every environment file it loads, and the CI job that runs it. A non-local host
    or a credential read records "not run" with the file and line. Otherwise the suite runs only in
    the credential-free environment #62 defines, and a failure there for want of a credential is
    recorded "not run", never retried outside it.
  - **Committed secrets are found only by a redacting scanner.** Phase 2.5 covers credentials in
    the working tree and in history, the way the `project-onboard` skill's "2.3 Secrets — find
    them without printing them" section does: a secret scanner with redaction on, recording only
    path, commit and line. With no scanner the record is "secrets: not surveyed", and the skill
    never substitutes a pattern of its own.
  - **Filing is optional.** The rule, verbatim: "**List the action plan.** File tickets only when
    the caller asks for them and `PROJECT.md` declares a tracker. File through the `issue-writer`
    skill, whose approval stop decides. When invoked as a survey, file nothing." Beside it, an
    exploitable finding is never filed into a tracker anyone outside the project can read, and a
    tracker not confirmed private counts as public; the finding stays in the report.
  - **Severity has a rubric, and the health score is gone.** Each level is defined by impact:
    Critical is broken today or money, data or access at risk now; High is latent risk to those
    under a reachable condition; Medium degrades correctness, cost or performance with none of them
    at risk; Low is maintainability, documentation or record-keeping drift. The executive summary
    no longer carries a 1–10 health score.
  - **The report is returned to the caller.** It is never written to a tracked file.
- **Context:** #65, from two audits of the skill on 2026-10-06. The first found that a step applied
  "only if PROJECT.md says the project uses" an integration, so the audit skipped exactly what it
  exists to discover, and during onboarding, with no `PROJECT.md`, every such step was skipped and
  the skip read as a clean result. It also found that "read-only against production data" covered
  only data writes, leaving a paid-API call, a test checkout, a sent message, a load test or a
  suite that hits live services unforbidden — each an effect a revert cannot undo (`CLAUDE.md` §6,
  escalation condition 8). The `project-onboard` review in #67 then showed that the old wording of
  the suite rule, "only when it needs no live service and no credential", is a condition only a run
  can reveal, while the shell may hold host tokens and production variables; reading the
  configuration first and running only in the credential-free environment answers that without a
  live experiment.

  **Why the new rules sit beside the read-only and filing rules, never inside them.** #67 quotes
  both rules verbatim from the `project-onboard` skill. Editing either would break that quotation
  silently, so every later finding adds a rule next to them.

  **Why the health score was dropped.** The second audit found that the score, like severity, had
  no rubric, so two runs on one codebase could score it differently and neither would be wrong. A
  severity rubric fixes the levels; a single number on top of it added nothing a reader could
  check. The owner chose to drop it on 2026-10-06.

  **Why the report never goes to a tracked file, and an exploitable finding never to a public
  tracker.** The report holds vulnerability details. This repository and its tracker are public,
  and a consuming repository may be too, so a tracked file or a public issue publishes the details.
  When privacy cannot be confirmed, the rule treats the tracker as public, which resolves doubt
  toward the safe side as `CLAUDE.md` §6 does.

  **Why the `allowed-tools` line leaves out Bash.** That line pre-approves the tools it names and
  restricts nothing. Leaving Bash out keeps a database CLI run behind its permission prompt; the
  written live-system rules remain the guard.

  **No relation.** D-30 records that this skill "files its finding tickets through the
  `issue-writer` skill". That stays true when the skill files at all, so this entry neither
  supersedes nor corrects it.
