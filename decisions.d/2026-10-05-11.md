# D-11 — 2026-10-05 — Every line in a diff must justify itself, and a line that cannot blocks approve

- **Decision:** `CLAUDE.md` §4 gains one rule, "Justify every line you write". Every line in a
  diff needs one of four reasons: the acceptance criteria require it, an existing caller needs it, a
  test covers it, or it repairs a defect the ticket names. Seven checkable shapes have no reason —
  a comment restating its code, an untested guard against an unreachable state, a helper or option
  with one caller or none, an abstraction for a second case that does not exist, replaced code left
  in place, a catch that does nothing or re-throws unchanged, and a docstring restating a visible
  signature. The rule names what it does not cover: it is not a line count, it never covers a
  tested guard (so §11 rule 3's required guards stay exempt), a test, or documentation that says
  more than its code, it judges the diff and never the surrounding code, and it governs code, never
  the prose of a document or a skill. §6 pre-merge check 1 names the rule. The `pr-reviewer` skill
  checks for each shape, quotes each matching line with its shape, records check 1 as `fail`, and
  returns `reject`. A line it cannot classify makes check 1 `unevaluable`, which escalates.
- **Context:** #11. An agent writing code tends to add lines the change does not need, each one
  individually defensible, so a reviewer approves a diff nobody could review line by line. §4 rule 7
  ("smallest change") is about scope, not density, and nothing else in the workflow governed it.

  **Why it blocks rather than advises.** The owner decided this on #11: unjustified code is a
  finding like any other, so the verdict is not `approve`, and escalation condition 6 sends the pull
  request to a human. An advisory note was the alternative, and it was rejected for the same reason
  the house style is advisory only where the owner chose that (D-29): a note is the right instrument
  for a rule the owner deliberately left unenforced, and the wrong one for a rule the owner wants
  enforced. A reviewer that only notes filler leaves the auto-merge tier open to exactly the diff
  this rule exists to stop. So the `pr-reviewer` skill's advisory section now says a matching line
  is never a note.

  **Why `reject` and not `escalate`.** The skill reserves `reject` for a pull request whose next
  action is fixing it rather than reading it, and removing a line that matches a shape is a fix.
  Both verdicts fire condition 6 identically, so the choice changes nothing about who merges. It
  also makes the finding a correctness defect under pre-merge check 1, which the repair block in §6
  already lists as repairable — the merge flow may delete the line itself. Where the reviewer cannot
  tell whether a line matches (a guard whose reachability it cannot establish, say), the check is
  `unevaluable`, and the existing fail-closed rule turns that into `escalate`. The rule is written
  to be checked, not weighed, so the shapes are predicates and the doubtful case goes to a human.

  **Why it governs code, not prose.** This repository's product is documents and skills, and the
  coordinator asked whether the rule reaches their prose. It does not: `STYLE.md` governs prose,
  and the owner ruled that guidance advisory (D-29). Extending this rule to prose would make it
  enforce the house style under a different name, reversing D-29 in passing. In this repository,
  therefore, the rule will rarely fire; it is written for the code of consuming projects.

  **Why the rule is stated once.** `CLAUDE.md` §4 holds the definition, because the implementing
  agent reads §4 before it writes. §6 and the `pr-reviewer` skill cite it. The skill carries the
  seven shapes as short labels so the reviewer can name a shape by number, and it points to §4 for
  the definitions and the exemptions.
- **Affects:** `CLAUDE.md` §4 (rule 7 and the new "Justify every line you write" block) and §6
  (pre-merge check 1); the `pr-reviewer` skill (§4 check 1, §6 advisory notes, §7 verdict and its
  `reject` definition, the quality bar); the `pr-merge-loop` skill's REPAIR phase, whose R3 shape
  ("a correctness defect in the diff") now includes an unjustified line; #11.
