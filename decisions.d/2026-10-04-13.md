# D-13 — 2026-10-04 — A ruleset enforces half the gate on `main`, and the owner applies it

- **Decision:** The default branch (`main`) gets one GitHub ruleset, named `main — merge gate`,
  enforcement `active`, with no bypass actors. It has four rules:
  1. **Require a pull request** before merging, with `required_approving_review_count` set to 0.
  2. **Require the `Markdown lint` status check**, pinned to the GitHub Actions app
     (`integration_id` 15368), the context name read from a real check run on `4fd3f18`.
  3. **Block force-pushes** (`non_fast_forward`).
  4. **Block deletion** of the default branch.

  **The owner applies the ruleset by hand, after the PR for #13 merges.** The owner ruled "Prepare
  only; I apply it" on 2026-10-04. No agent creates, edits or deletes the ruleset, or any other
  repository setting. The PR for #13 carries the exact payload. `PROJECT.md`, "Enforcement
  mechanism", says the gate is only honoured until the owner applies it, and names the call that
  shows whether it is live.

  **No `CODEOWNERS` file, for now.** Add one when a second person gets merge rights, or when
  outside contributions start to arrive. Revisit the approving-review rule in the same change.
- **Context:** `CLAUDE.md`'s merge gate was honoured by whoever merges and enforced by nothing:
  a direct push to `main`, a force-push, or a merge of a red pull request all went through. The
  repository is public (D-1), so rulesets are available on the Free plan, and #3 has given the
  ruleset a check to require.

  **Why no approving review is required.** GitHub refuses a pull request author's approval of their
  own pull request. On a one-person repository a required approval therefore makes every pull
  request unmergeable except by admin override. An override used routinely is worse than no rule,
  because it trains whoever merges to click past the gate — including on the day it is blocking
  something real. The independent review this project relies on is the `pr-reviewer` skill, under
  `CLAUDE.md` §6 escalation condition 6, and that verdict lives in a PR comment, not in a GitHub
  approval. A `CODEOWNERS` file is deferred for the same reason: it does nothing unless a rule
  requires a code owner's review, and that rule deadlocks a solo repository identically. The two
  are one decision, so they are revisited together.

  **Why the check is pinned to an app.** A required check named only by its context is satisfied
  by any commit status of that name, which anyone with write access can post through the API.
  Pinning it to GitHub Actions means only the workflow's own job can turn it green.

  **Why "require branches to be up to date" is off.** It forces a rebase and a fresh check run
  every time `main` moves, which serialises parallel lanes for little gain on a docs repository.
  `CLAUDE.md` §6 pre-merge check 4 already makes the merging flow re-check staleness itself.

  **Why no bypass actor.** A bypass list containing the owner would make the rules optional for the
  one account that merges almost everything here. With no bypass, an emergency change goes through
  a pull request like any other, or the owner disables the ruleset deliberately and visibly.

  **Why the owner applies it rather than an agent.** It is repository configuration, outside the
  diff, and it changes what every later session can do. The owner chose to keep that change in
  human hands. The cost is a window between this PR's merge and the owner's application, in which
  `PROJECT.md` must not claim enforcement it does not yet have. It says so, and gives the check.

  **What the ruleset does not cover.** The risk list, the footprint rule, the test rule, the size
  threshold, the reviewer's verdict, a stale record, the per-PR approval, and the rule that an
  agent never merges its own pull request stay honoured only. The server knows nothing about them.
- **Affects:** `PROJECT.md` ("Merge gate" → "Enforcement mechanism"); the repository's ruleset
  settings (applied out-of-band by the owner); every later pull request to `main`; #13.
