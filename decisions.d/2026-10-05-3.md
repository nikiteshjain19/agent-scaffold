# D-3 — 2026-10-05 — The green signal is the `Markdown lint` job, on pinned tooling

- **Decision:** This repository's green signal is the `Markdown lint` job in
  `.github/workflows/lint.yml`. It runs on every pull request to `main` and on every push to
  `main`, and it runs `npm ci`, then `npm run lint`. The lint tool is `markdownlint-cli2`, a dev
  dependency pinned to exactly `0.23.3`, with no caret, and `package-lock.json` is committed. The
  workflow pins each action to a commit SHA, with the tag in a comment. No link check is part of
  the gate. #3 specified the choice, and PR #24 (`4fd3f18`) shipped it.
- **Context:** Before #3, this repository declared no green signal. `CLAUDE.md` §0 therefore left it
  with no auto-merge tier, and every pull request waited for a human. That was correct while
  nothing checked a change, and #3 existed to build the check. Markdown lint is the check that fits
  a repository whose product is its documents: it is cheap, deterministic, and runs over every
  tracked `*.md` file. It checks form, never meaning, which is why `PROJECT.md` still risk-lists
  nearly every path.

  **Why the version is pinned exactly.** A caret range lets a new release of `markdownlint-cli2`,
  or of the `markdownlint` rules under it, arrive on the next `npm install` with no diff in this
  repository. A new or stricter rule could then turn the green signal red, or change what it
  accepts, on a pull request that changed nothing about linting. An exact pin plus a committed
  lockfile makes `npm ci` install the same tree locally and in CI, so a change to the gate shows up
  as a change to `package.json` — a risk-listed path, which escalates under condition 1.

  **Why the actions are pinned to commit SHAs.** A tag such as `v7` can be moved to point at other
  code, and this repository is public. A moved tag would run code nobody reviewed, inside the job
  that decides whether a pull request may merge. A commit SHA cannot be moved. PR #24 resolved each
  SHA from its release tag, and the workflow also runs read-only (`contents: read`) and does not
  persist checkout credentials.

  **Why a link check was left out.** The repository has few links, and the equivalent job in the
  private repository the scaffold grew in checked four of them. A link check also depends on remote
  sites being reachable, so it can fail with no change in this repository, which a green signal
  must never do. #3 put it out of scope. Add one in its own issue if the README grows.

  **How the check was proved.** PR #24 seeded a lint violation, watched the job fail locally and in
  CI, and reverted it. A check nobody has watched fail is not a check.

  **What this corrects.** D-1, "Open, and not decided here", records that no check runs on a pull
  request here. D-21's Context records that the project has no green signal yet. Both were true
  when written and are false since PR #24 merged. Neither decision is reversed: D-1 still publishes
  the scaffold as the `hivion` plugin, and D-21 still sets five cycles per run. Only a recorded
  statement of fact is stale, so the relation is `Corrects`, not `Supersedes`. #13 has since made
  the check a required status check on `main`, through the ruleset D-13 describes.
- **Corrects:** D-1, D-21.
- **Affects:** `PROJECT.md`, "Build / lint / test commands" and "Green signal";
  `.github/workflows/lint.yml`; `package.json`; #3; PR #24.
- **Corrected by D-51.** The green signal is still this job, but its `npm run lint` step now also
  runs the duplicate-id check over `decisions.d/`.
