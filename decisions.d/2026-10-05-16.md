# D-16 — 2026-10-05 — `CLAUDE.md` §0 routes on the repository's state, not on a missing `PROJECT.md`

- **Decision:** `CLAUDE.md` §0 is renamed "Project Bootstrap" and now routes before it asks
  anything. A missing `PROJECT.md` means only that the workflow is not adopted yet, and the words
  "start new project" start §0 without choosing its path. The path comes from a mechanical test:
  the project is existing when the repository's history touches a path outside the scaffolding
  set, or when the tracker the owner names holds an open issue; it is new when neither holds. The
  scaffolding set is exactly `CLAUDE.md`, `STYLE.md`, `PROJECT.md`, `README.md`, `LICENSE`,
  `.gitignore`, `decisions.d/` and `.claude/`. A repository with no commit does not meet the
  history condition, and the failing `git log` there reads as "not met", not as unreadable
  history. An owner who names no tracker does not meet the tracker condition. The test is
  ambiguous in four cases, and each one is put to the owner: the history cannot be read; the named
  tracker cannot be reached; the result contradicts how the owner describes the project; the
  `project-onboard` skill's own precondition check disagrees with the test. §0 never defaults to
  the new-project path. A new project runs the §0 interview as before; an existing one runs the
  `project-onboard` skill instead. That skill's "0. PRECONDITIONS" step 2 no longer carries a test
  of its own: it runs §0's test by citation, hands back to §0 when the test says new, and asks the
  owner when §0 calls the result ambiguous.
- **Context:** #16. #15 (D-15) added the `project-onboard` skill for adopting the workflow into a
  project that already exists, and left the routing to this issue. Before this change §0 ran
  "when `PROJECT.md` is missing", which is true of every repository that has not adopted the
  workflow yet — a five-year-old codebase as much as an empty directory. The interview then asked
  what v1 looks like and told the agent to create initial milestones and tickets, so a halfway-built
  project got a `PROJECT.md` describing an intention rather than the repository. That document is
  confident and wrong, and every later agent trusts it. The asymmetry is why §0 never defaults to
  the new-project path: adoption run on a nearly empty repository only reports that little exists,
  while the interview run on an existing one writes a false record.

  **Why a mechanical test, not a judgment.** "Does this look like an existing project?" is the kind
  of question two agents answer differently. A path list and an issue count are facts any agent
  reads the same way, so the routing is reproducible and a reviewer can check it. The scaffolding
  set is enumerated because those are the files a fresh repository starts with or the workflow
  itself adds; a repository whose history holds nothing else has had the workflow dropped into it
  and nothing built. The tracker condition exists because a project can have a backlog and no code
  yet, and the interview would then file "initial tickets" beside a backlog it never read.

  **Why one test lives in §0 and the skill cites it.** PR #43's review found that the
  `project-onboard` skill carried its own test — a commit count, where one commit meant new — which
  disagreed with §0's path test: a repository whose first commit already held code was new to the
  skill and existing to §0. Two tests for one question drift, and an agent obeying both sends the
  same repository down opposite paths. §0 owns the routing, so the test is written there once and
  the skill points to it by section rather than restating it. The fourth ambiguous case stays in §0
  even though the skill now cites the test: a skill is installed per machine, so an older install
  can still carry the commit count, and a disagreement then reaches the owner instead of being
  settled silently.

  **Why not `Corrects: D-15`.** D-15 records the skill's phases, its adoption rules and its
  fail-closed defaults. It does not record the commit-count precondition as a decision, and it
  states that routing §0 to the skill is #16's, not part of D-15. Nothing D-15 decided changes
  here, so neither relation applies.
- **Affects:** `CLAUDE.md` §0 and the paragraph above it; `PROJECT.md` line 7 (the scope note on
  how a repository writes its `PROJECT.md`); the `project-onboard` skill, "0. PRECONDITIONS"
  step 2; #16; PR #43.
