# D-30 — 2026-10-05 — Every issue is created through the `issue-writer` skill, which gains a pre-approved path

- **Decision:** Every issue is created through the `issue-writer` skill, never written by hand.
  `CLAUDE.md` §2 states the rule, and §0 (the initial tickets), §4 step 7 (a scope-creep ticket) and
  §5 rule 4 (dependency links) point at it. When a session cannot invoke the skill, in the sense
  §12 defines, the agent stops and asks the user; it never falls back to a hand-written issue. The
  `issue-writer` skill gains a pre-approved path, a subsection of "5. PRESENT THE PLAN", for one
  issue the owner has already approved by its problem and its scope, in the session or in a tracker
  comment. That path skips only the §2 CLARIFY round and the §5 stop, and still runs the research,
  the full issue anatomy, the quality bar and the filing steps. It applies only to one PR-sized
  issue whose research raises no question that would change it; otherwise the run falls back to the
  §5 stop. The `project-audit` skill files its finding tickets through the `issue-writer` skill.
- **Context:** On 2026-10-04 an agent filed follow-up issue #27 from a freehand brief. It came out
  with `## Footprint` and no `## Wave`, and the `issue-loop` skill reads neither shape, so it treated
  #27 as declaring no footprint. Two causes sat behind that. `CLAUDE.md` §2 said "If asked to do
  something without one, create the ticket first (title, description, acceptance criteria), then
  start", which permits a hand-written issue. And the `issue-writer` skill always stopped for plan
  approval, so for a small follow-up the owner had already approved, the agent bypassed the skill
  rather than ask twice. Closing only the first cause would have made the rule costly enough to be
  bypassed again; closing only the second would have left a hand-written issue permitted. The owner
  approved this scope on 2026-10-04, after #27, and confirmed on 2026-10-05 that the
  stop-and-ask rule for a session that cannot invoke the skill is in scope.

  **Why the pre-approved path still prints the plan.** The issue says the path skips the §5 stop
  "and nothing else". The plan printout is part of §5 but is not the stop, so the path keeps it:
  the user still sees what is about to be filed, and nothing waits on it.

  **Why a single issue only.** Approval of a batch, or of a feature that needs decomposing, is
  exactly where the §5 review earns its cost, because the slicing is the judgment being approved.
  The approval wording mirrors `CLAUDE.md` §6, approval gate rule 1, so that "keep going", silence
  or approval of a different item never count, here or at merge.

  **What was left alone.** The `project-onboard` skill, merged after #30 was filed, tells the agent
  in its WRITE phase to "Create the adoption ticket". That instruction sits outside #30's declared
  footprint, so it was reported on #30 rather than edited. `CLAUDE.md` §2 now governs it all the
  same.
- **Affects:** `CLAUDE.md` §0, §2, §4 step 7, §5 rule 4; the `issue-writer` skill (front matter
  `description`, the "Approval before filing" property, "5. PRESENT THE PLAN", "6. FILE THE
  ISSUES", "8. HARD RULES"); the `project-audit` skill (the "Issue tracker" input and the
  "Immediate action plan" output item); the `project-onboard` skill's WRITE step 1, reported but not
  changed; #27; #30.
