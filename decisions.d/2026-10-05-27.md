# D-27 — 2026-10-05 — The default risk list protects a modified or deleted decision entry, never an added one

- **Decision:** `CLAUDE.md` §0 topic 7's "always risk-listed" part no longer names the decision log
  directory as a whole. It names a modified or deleted entry in it, and never an added one. A new
  entry is an ordinary change, because it binds only through the files it changes. An edit to an
  existing entry always escalates, including a `Supersedes` or `Corrects` back-reference, and so
  does a deleted entry. §6 escalation condition 1 gains a change-type qualifier: a risk-list entry
  may name the change types it covers, such as "modified or deleted". The reviewer reads each
  matched file's change type from the diff, counts a rename as a deletion plus an addition, treats
  an entry with no qualifier as covering every change type, and treats an unreadable change type as
  covered. §0 topic 7 tells a project to write the decision-log line as `decisions.d/**`, modified
  or deleted only. The `pr-reviewer` and `pr-merge-loop` skills note the qualifier when they read
  the risk list, and apply it in their condition 1 step through
  `git diff --name-status --no-renames origin/<BASE>...<SHA>`. This repository's own `PROJECT.md`
  risk list keeps `decisions.d/**` with no qualifier, so here every decision entry still escalates.
- **Context:** #27. PR #26 (#12) added the default risk list with the whole of `decisions.d/` on
  it. §7 makes nearly every PR that involves a judgment call add a decision entry, and condition 1
  fires on any risk-listed path, green signal or not. A consuming project that copied the default
  would therefore send nearly every PR to a human for its decision file alone, and the auto lane
  would be unreachable for ordinary work. That is the "protects too much" failure D-12 set out to
  prevent. The repository owner agreed the narrower rule on 2026-10-04.

  **Why an added entry is safe to leave off, and the other two are not.** A decision that changes
  the gate, a spend cap or the risk list has to edit `CLAUDE.md` or `PROJECT.md` to take effect,
  and both stay always risk-listed, so such a decision still escalates through those files. An
  edit to an existing entry is different in kind: a `Supersedes` or `Corrects` back-reference
  switches off or rescopes a rule agents follow today, and nothing else in the diff need show it. A
  deletion contradicts §7's append-only rule outright, so it is never routine.

  **Where the mechanism lives — both places, with different jobs.** Condition 1 matches paths
  against gitignore-style globs, and a glob cannot tell an added file from a modified one, so
  `decisions.d/**` on a list fires on every new entry whatever §0's prose says. Prose in §0 alone
  would not reach the reviewer, which reads condition 1 and `PROJECT.md`, never §0. A qualifier in
  condition 1 alone would leave a consuming project without the shape to write. So condition 1
  carries the generic rule the reviewer applies, and §0 topic 7 carries the one line a project
  writes. The qualifier is generic rather than special to the decision log, because condition 1
  reads only what the project's list declares: a hard-coded carve-out would have changed what this
  repository escalates while its `PROJECT.md` stayed unchanged, which #27 puts out of scope. The
  default for an unqualified entry and for an unreadable change type is "covered", matching §6's
  tie-break that a condition which cannot be evaluated counts as met. `--no-renames` makes git list
  a renamed entry as a deletion of its old path, so a rename inside the log still escalates.

  **The residual risk.** A new entry could reinterpret a rule without touching a risk-listed file,
  because agents read the log before implementing (§4) and apply what it says. Pre-merge check 2
  reads entries dated after a PR's branch point, so it checks a PR against decisions already on
  the default branch. It does not judge whether the entry a PR adds is itself a quiet
  reinterpretation, so it does not close the gap; check 1 reads the entry, but as a correctness
  review, not as a predicate. The PR that closes #27 proposes the extra check as a follow-up,
  rather than widening the list back.

  **Why `Corrects`, not `Supersedes`.** §7 asks whether the earlier decision still binds. D-12's
  decision stands: a default risk list in two parts, the eighth escalation condition and the
  condition 4 wording are all unchanged. This entry narrows one line of that list, which changes
  D-12's scope, the case §7 assigns to `Corrects`.
- **Corrects:** D-12 — the decision log line in the "always risk-listed" part of the default list.
- **Affects:** `CLAUDE.md` §0 topic 7 (the default risk list) and §6 escalation condition 1; the
  `pr-reviewer` skill (§1 CONFIG, the risk-list input; §5 condition 1); the `pr-merge-loop` skill
  (CONFIG, the risk-list input; CLASSIFY condition 1); D-12 (`decisions.d/2026-10-04-12.md`);
  `PROJECT.md` ("Merge gate" → "Risk-list paths", unchanged); #12; PR #26; #27.
