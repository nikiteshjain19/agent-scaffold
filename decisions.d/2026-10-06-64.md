# D-64 — 2026-10-06 — The `issue-loop` skill reserves every open PR's files, releases every bounced claim, and moves the stacked lane to a reference file

- **Decision:** The `issue-loop` skill changes in seven ways that shape how future runs behave.
  1. **The refill scope is the full reservation set.** §6 item 7 tests a refill candidate against
     every in-flight lane and the whole reservation set of §1 step 8: every open PR whose base is
     the default branch, or whose base is another open PR's head branch, whoever opened it. A
     refill from the waiting dispatch wave re-runs §1 steps 8–9 first (§6 item 8).
  2. **An undeclared lane budget means one lane** (§0 step 4).
  3. **The stacked lane has a merge-strategy precondition, and its parent may come from an earlier
     run.** A child stacks only when `PROJECT.md`'s merge strategy merges a stacked parent with a
     merge commit and keeps its branch, as its ordinary strategy or as a declared exception. The
     parent is an issue whose PR is open and green, whether this run or an earlier run opened it.
  4. **Plan-wave numbers are scoped to their plan.** §1 step 7 compares `## Wave` numbers only
     between issues whose `## Wave` names the same plan file. Across plans, and against "none",
     it orders by priority, then by age.
  5. **A hazard is defined through the declared footprint, with no separate list.** §6 item 5
     states what each hazard's footprint must declare: the manifest and lockfile, the generated
     output, the rewritten directories, or a migration's directory. The disjointness test then
     holds hazards apart on its own. The solo-wave rule for hazards and the `single-lane hazard`
     reason are gone.
  6. **The dispatch wave is uncapped, and each issue is claimed at its own dispatch.** §1 step 8
     adds every candidate that passes. The lane budget caps the running lanes (§6 item 4). §6
     item 1 claims an issue immediately before its lane is dispatched, so a waiting member stays
     unclaimed, and §6 item 8 refills from the waiting members.
  7. **The stacked lane lives in `plugins/hivion/skills/issue-loop/references/stacked-lane.md`.**
     §1 step 5 keeps the trigger and a one-sentence pointer, and §7 keeps the hard rule that a
     stacked child never merges before its parent.
- **Context:** #64, from two audits of the `issue-loop` skill on 2026-10-06. The owner approved
  the issue's plan ("I'm good with all the changes. Let's go ahead.") and asked for the second
  audit's points to land in the same issue rather than in a duplicate.

  **Why the refill scope widens, and how it departs from private D-108.** That entry kept the
  refill test narrower than wave selection: a refill was tested only against in-flight lanes and
  the open PRs this run opened, while wave selection tested every open PR. The narrower scope let
  a refill hand a new lane the files of a PR an earlier run left open, or of an open stacked child,
  because wave selection's own set also covered only PRs based on the default branch. A PR an
  earlier run opened collides exactly as one this run opened does, so one set now serves both
  tests, and it includes PRs based on another open PR's branch. No `Supersedes` or `Corrects` is
  written, because private D-108 is not in this repository's log.

  **Why one lane by default.** A missing budget defaulted open, to three lanes, so a project that
  never declared a budget ran in parallel without choosing to. One lane is the fail-closed reading:
  parallelism is a choice the project declares in its "Parallelism" section.

  **Why the stacked lane needs a merge-strategy precondition, and an earlier-run parent.** The
  child's safety rests on the parent merging with a merge commit and keeping its branch; a squash
  that deletes the branch re-includes the parent's changes in the child's diff. The lane used to
  cite that fact to `PROJECT.md`'s "Toolchain" section, where no such row existed. The fact is the
  `pr-merge-loop` skill's STACKED PAIRS item 3, so the lane now cites that skill and requires the
  project's merge strategy to provide it. A parent dispatched in the same wave has no PR yet and
  its branch holds nothing to build on, so the condition "a parent in this run's wave" could never
  fire usefully. Under the `cycle-manager` skill, one wave per run (#66) means the parent always
  comes from an earlier run.

  **Why wave numbers are plan-scoped.** Two unrelated plans each number their waves from 1, so a
  global "lowest-numbered wave" ordered one plan's wave 2 behind another plan's wave 1 for no
  reason. A plan's wave order means something only inside that plan.

  **Why hazards go through the footprint, and not through a list.** A hazard list asks the
  coordinator to notice an operation and then run it alone, which fails silently when the
  coordinator does not notice. The risk list cannot serve: it decides who approves a merge, and
  here it holds `plugins/**`, so every issue would run alone. A footprint that declares an
  operation's whole reach makes the existing disjointness test sufficient, because a directory
  intersects every path beneath it. The owner rejected adding a new list when a risk list and a
  declared footprint already exist.

  **Why the dispatch wave is uncapped and claimed per dispatch.** Capping the wave at the lane
  budget left §6 item 8's "refill from the current wave first" with nothing to refill from.
  Claiming every wave member before any lane ran left a waiting member assigned and unavailable to
  another session, with no lane working it.

  **Why the stacked lane moves to a reference file.** It filled about a sixth of the skill for an
  opt-in case that this repository cannot use until its merge strategy changes (#63). Every run
  read it. A trigger and a pointer keep the exception reachable, and every cited step number stays
  in place.
- **Affects:** the `issue-loop` skill (front-matter `description`; "Why waves"; §0 steps 1–4; §1

  `plugins/hivion/skills/issue-loop/references/stacked-lane.md`; the `issue-writer` skill (§3 size

  files or the facts they cite.
