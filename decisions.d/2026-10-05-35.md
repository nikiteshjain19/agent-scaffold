# D-35 — 2026-10-05 — A wave may run up to five lanes

- **Decision:** `PROJECT.md`, "Merge gate" → "Parallelism", raises **Max lanes** from 3 to 5. The
  cycle cap (5) and the repair-round cap per pull request (3) stay as they are.
- **Context:** The owner asked for this on 2026-10-05, to work more issues in parallel per wave.
  The `issue-loop` skill reads its lane budget from that section and never runs more lanes than it
  declares, so the number had to change in `PROJECT.md`.

  **The trade-off, stated plainly.** Footprint disjointness and the single-lane hazards still bound
  every wave, so 5 is a ceiling, not a target: a backlog with only two disjoint eligible issues
  still runs a wave of two. More lanes means more open pull requests at once. An unmerged pull
  request keeps its footprint reserved until it merges or closes, and most pull requests here wait
  for a human approval because nearly every path is risk-listed. Extra lanes may therefore sit
  idle, waiting for a footprint to free up rather than doing work. The open-PR window grows with
  the lane count, and with it the conflict risk the `issue-loop` skill names in §6 item 6, which
  asks a run to keep that window near the lane count.

  **Why `Supersedes`, and only for the lane cap.** `CLAUDE.md` §7 asks whether the earlier decision
  still binds. D-21's sentence "The lane cap (3) and the repair-round cap per pull request (3) stay
  as they are" no longer binds for the lane cap: a reader who applied it would hold the project to
  three lanes. That clause is off, so the relation is `Supersedes`. The rest of D-21 still binds —
  its cycle cap of five, and its statement that the repair-round cap stays at 3 — so the relation
  is limited to the lane-cap clause.
- **Supersedes:** D-21, the lane-cap clause only ("The lane cap (3) … stay as they are"). D-21's
  cycle-cap decision still binds.
- **Affects:** `PROJECT.md` ("Merge gate" → "Parallelism"); the `issue-loop` skill's reading of the
  lane budget; D-21 (`decisions.d/2026-10-04-21.md`); #35.
