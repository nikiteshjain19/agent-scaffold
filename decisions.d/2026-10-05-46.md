# D-46 — 2026-10-05 — A decision citation names its log: bare, `scaffold` or `private`

- **Decision:** `CLAUDE.md` §7 gains one rule, "A citation names its log". Every decision citation
  takes one of three forms. A bare `D-N` names an entry in the reading repository's own
  `decisions.d/`. `scaffold D-N` names an entry in the scaffold's public log, the `decisions.d/` of
  the repository that publishes `CLAUDE.md` and the skills. `private D-N` names an entry in the
  private log of the repository the scaffold grew in, which no reader outside it can open. The
  documents that travel to a consuming repository — `CLAUDE.md`, `STYLE.md` and every skill — never
  write a bare `D-N`. A marked citation is provenance only: the sentence around it states
  everything the reader needs, and no instruction depends on opening the entry. In this
  repository a bare `D-N` and `scaffold D-N` name the same log. Every citation in `CLAUDE.md` and
  the skills now follows the rule: of the thirty-nine citations, seven name this repository's own
  entries (D-5, D-11, D-12) as `scaffold`, and thirty-two name private entries as `private`. Where a
  sentence leaned on the id to carry its meaning ("D-77 stands untouched", "the failure D-155
  describes", "D-108 stays in force"), the sentence now names the rule itself and keeps the id in
  parentheses. §7's "Legacy ids stay as they are" now speaks of any log that holds counter-numbered
  entries, rather than naming `D-001` and `D-002` as entries this repository does not hold, and
  keeps its rule that a legacy entry is never renumbered. The "Format per entry" example now uses
  placeholders (`D-<N>`, `D-<S>`, `D-<C>`, `<YYYY-MM-DD>`) instead of D-42, D-017 and D-018. §7's
  "D-70 could not write its back-reference" now reads "private D-70".
- **Context:** #46. `CLAUDE.md` and the skills cite decisions by id, and most of those ids name
  entries in the private log of the repository the scaffold grew in. That log stayed private when
  the scaffold was copied here (D-1), so none of those files exists in this repository. Since §7
  derives a decision's id from its issue number, the two id spaces overlap. #37 will create D-37
  here, while §0 cited a private D-37 with a different meaning. #19 would create D-19, which the
  `issue-loop` and `issue-writer` skills cited for a different decision. Later issues reach D-70,
  D-77, D-108, D-155 and the rest. §7 says two entries must never claim one id, and the same
  sentence-level collision applies to citations: a reader who sees "D-37" in §0 after #37 merges
  opens the wrong entry.

  **The consuming-repository case is the larger one.** `CLAUDE.md` and the skills travel to every
  consuming repository, whose own log derives ids from its own issues. There every cited id —
  this repository's D-5, D-11 and D-12 included — pointed at a file the consumer cannot have, and
  could collide with the consumer's own entry. So the rule reserves the bare form for the reading
  repository's own log, which is the only log every reader holds, and marks everything else.

  **Why the citations change, not the entries.** §7 is append-only and forbids renumbering a
  legacy entry. The private entries are not ours to renumber anyway, and this repository's entries
  are already issue-derived. Renumbering would also break every citation of them already written
  in PR bodies, issue comments and other entries. The citation is the only thing a document here
  controls, so the citation carries the log.

  **Alternatives rejected.** A link to each scaffold entry's file in the public repository was
  considered for this repository's own entries. It would let a consumer open the entry, but it
  covers only one of the two foreign logs, adds a long URL to every citation, and ties the
  documents to one host path — the same objection `CLAUDE.md` §12 makes to a path for a skill.
  Removing citations was considered too. It would lose the provenance a later reviewer uses to
  find why a rule exists, and the rule already makes a kept citation harmless, so nothing was
  removed. A marker naming only the private log ("private log D-77", the issue's example) was
  rejected because it leaves this repository's own entries bare in documents that travel, which
  is exactly the consumer collision above. One word per log keeps every citation short, and a
  reader can tell the log from the citation alone.

  **Two existing entries cite a private decision in the bare form.** D-11's Context cites
  "D-29" three times ("the owner chose that (D-29)", "the owner ruled that guidance advisory
  (D-29)", "reversing D-29 in passing"), and D-5's Context cites it once ("the owner left the
  house style unenforced (D-29)"). Under this rule each of those is private D-29, the private
  decision that the house style is advisory and nothing enforces it. Neither entry is edited, since
  §7 is append-only. This entry is the record a reader uses to resolve them. #14 plans a
  `Corrects` relation to that private entry, and should write it in the marked form.

  **No relation.** §7's test asks whether an earlier entry still binds. No earlier entry in this
  repository decided how a citation is written, so nothing here is superseded or corrected. D-11
  and D-5 stand unchanged; this entry only says how to read one id inside them.
- **Affects:** `CLAUDE.md` §0 (the `PROJECT.md` bullet, the default risk list paragraph), §6
  (pre-merge check 1, the review-record paragraph, escalation condition 8, approval gate rule 2,
  the repair block), §7 (the new rule, "Legacy ids stay as they are", the format example, the
  back-reference sentence) and §9; the `issue-loop`, `issue-writer`, `pr-merge-loop`, `pr-reviewer`
  and `cycle-manager` skills; D-11's and D-5's citations of D-29 (read as private D-29); #14; #19;
  #37; #46.
