# D-20 — 2026-10-06 — Every finished pull request reaches a merger, a question carries across cycles, and a moving head stops after two moves

- **Decision:** The `cycle-manager` skill's C8 gains a fifth loop predicate: "The head commit moved
  under two of this pull request's verdicts in this run." The two run predicates are renumbered 6
  and 7, and their meaning is unchanged. Predicate 5 counts every verdict discarded because its
  `HEAD` no longer equals the pull request's current head, wherever the discard happens: DRIVE
  step 3, the head check before a merger is dispatched, the head check on a carried pull request,
  and a merger that stops on a void verdict. A pull request it stops gets no merger and no digest
  entry, stays open, and is named in the digest and the run report with each discarded `HEAD` and
  the head that replaced it. C1 to C7 are unchanged.

  Beside that contract change, the MERGE phase now sends every finished pull request to a merger,
  by one of two routes. An `approve` verdict takes the direct route, after DRIVE and before the
  digest, carrying `not yet approved` and no head, so the merger's auto lane merges it without a
  question. Every other verdict takes the digest route, carrying the user's answer. A question that
  arises after a cycle's digest is carried into the next cycle with its verdict block; its head is
  read at the start of that cycle, and a moved head sends it back to DRIVE for a fresh review
  instead of to the digest. When the run stops with a carried question, one closing pass (DRIVE,
  the direct route, a digest and the digest route, with no wave) asks it; anything that pass raises
  is printed and left open. A merger's `hard-stops` entry is asked in place before the next
  dispatch, the answer is recorded verbatim, and that pull request and every pull request its
  question names are held out of later mergers and reported, because no merger step can carry a
  lock ruling out.
- **Context:** #20, from a design review on 2026-10-04 that found four defects in the cycle
  manager. An approved pull request with no question was in neither MERGE's list nor the digest's,
  so it never merged. A merger's question printed in the next cycle's digest had no path back to a
  merger, and a question raised in the last cycle was never asked at all. DRIVE step 3 discarded a
  verdict whose head had moved and re-dispatched without advancing the round, so a branch that kept
  receiving commits looped without end. C6 carried `hard-stops`, and no section read it.

  **Why the manager routes by the verdict's first line and decides no lane.** The issue sends an
  auto-tier pull request to the merger "directly, with no digest entry", but the manager reads none
  of the gate's inputs and re-decides no rule, so it cannot know the tier. The verdict already
  carries the one fact the manager may read: a verdict other than `approve` meets escalation
  condition 6, so that pull request is in the escalation tier by `CLAUDE.md` §6 alone. An `approve`
  verdict is necessary for the auto tier and not sufficient, so the merger still classifies it. When
  the merger escalates it after all, its queued question still reaches this cycle's digest, because
  the direct route runs before the digest. The alternative, dispatching a merger for every pull
  request before any digest, would also have worked, but it adds a merger dispatch for every
  pull request the reviewer already escalated, only for that merger to queue the same question the
  manager can build from the verdict.

  **Why the move cap is per pull request per run, and why two.** The issue asks to "stop after the
  head commit moves twice" and to name the stop "as a predicate a reader can check". A count per
  round would let three rounds take six moves, and a count per DRIVE entry would reset every time a
  carried pull request re-entered DRIVE, so neither bounds the run on its own. A count per run is
  the simplest number a reader can verify from the report, and it bounds every path that re-reviews
  a pull request, including the new head checks before a merger and on a carried pull request.

  **Why it is a C8 predicate, and why the run predicates are renumbered.** C8 is where the skill
  names every stop, and the run report's "Stop predicate" column reads it. Appending the new loop
  predicate after the run predicates would split the loop predicates in two. The only citations of
  the old numbers 5 and 6 are inside the skill's own ASSESS phase, which this change updates; D-5
  cites predicate 3, which keeps its number.

  **Why a hard stop's answer is recorded and not relayed.** The issue asks for a handler where the
  digest handles its two in-place questions. The `pr-merge-loop` skill's SINGLE-PR MODE has no step
  that reads a lock ruling or a destructive-action confirmation, and A RELAYED ANSWER reads only a
  merge approval. Relaying the ruling through C5 would make the merger build a card, find the same
  lock in its scoped PROBE, and ask again. Holding the named pull requests out of the run is the
  fail-closed reading of `CLAUDE.md` §13, which keeps both items blocked until the user rules, and
  the run report names the full `pr-merge-loop` run that carries the ruling out. Giving SINGLE-PR
  MODE a way to read a ruling would edit that skill, which is outside this issue's footprint.

  **Why a stopped merger's question is printed and never routed.** A merger in SINGLE-PR MODE
  queues two kinds of question: its review card's merge question, and the question that closes a
  stop, such as a conflict with the base branch. Only the first has an answer a later merger can
  act on, because that mode resolves no conflict and releases no hold. Routing a stopped merger's
  question through the digest would dispatch a second merger on the verdict the first one stopped
  on, which the MERGE phase forbids. So "stopped" means that mode took a stop, a merger waiting on a
  merge question has not stopped, and a merger the manager cannot place counts as stopped, because
  a stop dispatches nothing. A stopped merger's pull request gets no digest entry and is named in
  the run report, for a full `pr-merge-loop` run to handle.

  **Why the closing pass carries nothing further.** Without a bound, a closing pass that raised a
  question would need another closing pass. One pass asks every question the last cycle carried,
  which is the gap the issue names, and anything after it is printed rather than lost.

  **No relation.** D-7 named what the merger does with a relayed answer and left the routing to
  this issue; that entry still binds unchanged, so it is neither superseded nor corrected. D-5 and
  D-6 are untouched.

  **Why this is a decision.** The `cycle-manager` skill says its contracts are frozen and that
  changing one is a decision (`CLAUDE.md` §7). This entry is the record that the owner approves the
  C8 change knowingly, with the pull request that makes it.
- **Affects:** the `cycle-manager` skill (the opening paragraph, C8 and the paragraph after it,
  WAVE steps 5 to 8, DRIVE's opening, steps 3, 4 and 8 and the two paragraphs after them, DIGEST,
  MERGE and its three new subsections, ASSESS, a HARD RULES bullet, and the RUN REPORT); #20; #34,
  which edits the DRIVE and MERGE sections this change rewrites.
