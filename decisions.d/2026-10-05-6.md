# D-6 — 2026-10-05 — `pr-merge-loop` gains a single-PR mode, and C5 and C6 name it

- **Decision:** The `pr-merge-loop` skill has a SINGLE-PR MODE. A caller enters it only when the
  invocation names one pull request and asks for a `CYCLE-MERGE-RESULT` block, which is the
  `cycle-manager` skill's C5 brief. In that mode the run skips SETUP's batch listing. It reads the
  open PR list once, to check that its one PR's base is BASE, and to check it for a stacked child
  and a parent with an open child. It runs PROBE scoped to its one PR: the per-PR steps, the schema
  check, and the cross-diff pass for every pair that includes its PR. Any cross-diff finding against
  another open PR, a shared file included, holds its PR as a possible lock. The run writes to that
  PR, its ticket and the tickets that ticket blocked, and no other PR. It writes no commit, so it
  resolves no conflict and makes no repair. Every stop returns the `CYCLE-MERGE-RESULT` block that
  the `pr-merge-loop` skill defines in that section, with the four fields `merged`, `still-open`,
  `queued` and `hard-stops`. The PROBE rules in that skill name the scoped run as their one
  exception to a full run. C5 gains the words "in its single-pull-request mode". C6 gains a sentence
  that names the `pr-merge-loop` skill as the definition of its block. C6's four field names are
  unchanged.
- **Context:** #6, from an audit on 2026-09-18. C5 told a merger to run `pr-merge-loop` "against one
  pull request", and C6 expected a `CYCLE-MERGE-RESULT` block back. `pr-merge-loop` had neither. It
  listed every open PR, probed the whole batch, and dispatched its own reviewer for any PR without a
  verdict. A merger dispatched for one PR would therefore work the whole queue, so it broke the
  manager's stated properties: every agent is a sibling, and the merger writes no commit.

  **Why the mode, and not a change to C5 and C6.** The issue offered both. No section of
  `pr-merge-loop` takes one PR and returns a block, so the other option would have had to rewrite the
  C5 brief into the full loop's terms, and the caller would then lose the one-PR design the manager
  depends on. The mode keeps C5 and C6 close to their current meaning and gives the merger a single
  defined path. It also keeps the verdict relay, the escalate lane and the merge steps of the full
  loop, so no merge rule is re-decided.

  **Why the mode never writes a commit.** The manager's design says the merger writes no commit, and
  a conflict resolution or a repair would change the head SHA. That would void the verdict that
  authorised the merge, so the merger would have to stop anyway. A conflict or a defect therefore
  stops the merge and leaves the PR open, and the question goes to the user. A conflict's question
  reaches the user as a queued ASK block, which the merger counts in its `queued` field.

  **Why the mode runs PROBE scoped to its PR, and does not skip it.** PROBE is the only detector
  for a semantic conflict between PRs that share no file, and the only step that checks a migration
  against the live schema. An earlier draft of this PR skipped PROBE and held only on a shared file.
  Review found that this let a semantic conflict across different files, and an unchecked
  migration, merge unattended. It also contradicted the skill's own rule that PROBE is never
  skipped. The scoped run keeps every check that bears on this PR. It drops the pairs that exclude
  this PR, because they do not change whether this PR may merge. It drops the risk map and the order
  question, because one PR has no order to decide. Any cross-diff finding against another open PR,
  a shared file included, holds this PR as a possible lock, and the user rules on it. This is
  fail-closed. It can hold a PR that is not truly locked, and the user then clears it.

  **Why a stacked parent is held and not merged.** Its child needs a retarget, and a retarget writes
  to the child PR. This mode writes to no other PR, so it holds the parent. The ordinary merge path
  still handles the parent in a full run.

  **Why a PR whose base is not BASE is held.** A merge would land on that base branch and never
  reach BASE, yet the merge steps would still close the ticket and sweep its dependents. A child
  whose parent merged but was never retargeted is the case this catches. The full loop lists only
  PRs based on BASE, and retargets such a child before it works it. This mode writes to no other
  PR, so it holds the PR and leaves the retarget to a full run.

  **Why the dependent sweep stays.** `cycle-manager` gives the merger the ticket update and the
  dependent sweep, and `CLAUDE.md` §6 requires the sweep after every merge. The sweep writes only to
  tickets that the merged ticket blocked. It writes to no PR, so the mode's one-PR scope holds.

  **Why this is a decision.** The `cycle-manager` skill says its contracts are frozen and that
  changing one is a decision (`CLAUDE.md` §7). The skills it composes build against C5 and C6, so
  this entry is the record that the owner approves the change knowingly, with the pull request that
  makes it.
- **Affects:** the `pr-merge-loop` skill (a new SINGLE-PR MODE section before SETUP, the final line
  that sends an invocation to it, and the PROBE exceptions in its ASK BLOCK, PROBE and RULES
  sections); the `cycle-manager` skill (C5, and the sentence after C6); #6.
