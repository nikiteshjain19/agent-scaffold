# D-68 — 2026-10-07 — The independent reviewer approves a footprint widening, reported in bold, and footprint checking has no setting

- **Decision:** Footprint checking is always on, and an extra file is approved only by a widening
  the independent reviewer approves. The change has six parts.
  1. **Who requests, who decides, who records.** The implementer requests a widening in the PR body,
     in the `## Footprint widening request` form, and never approves one. The `pr-reviewer` skill
     decides each requested path under escalation condition 3. Only the reviewer approves a path,
     and only for a quoted acceptance criterion, or for a quoted document passage it confirmed by
     reading is false. A requested risk-listed path goes to the owner, and condition 1 still fires.
     The merger writes each approved path into the issue's `## Declared file footprint`, reads it
     back, and merges nothing when the write fails.
  2. **The owner's approval covers the file list only.** On an escalated PR, approving the PR also
     approves each extra file the review card names in bold. That approval never overrides a failing
     or missing check, or another hard stop.
  3. **The bold report rule.** Every approved widening appears in bold in the run report, with its
     PR, issue, path, reason, approver and head. It also appears on the PR's review record and on the
     issue. A request no reviewer has decided appears in bold in the `issue-loop` run report. It
     also appears in bold on the escalate-lane review card, as a fourth line beside the three
     frozen ones. A PR that touches a risk-listed path often escalates with no reviewer, so its
     request would otherwise get no line and no record. The owner approved this line on 2026-10-06.
  4. **The repairer's request-and-stop rule.** A repairer that needs a file outside the footprint
     writes a request in the PR body, then stops. It never touches that file. The reviewer alone
     decides the request.
  5. **The footprint-enforcement setting is removed.** No skill reads an on or off field from
     `PROJECT.md`. Condition 3 applies in every project. `PROJECT.md` keeps its "Footprint enforcement"
     section, with the rule in its body, so that a reader and an older installed skill still find it.
  6. **The merger writes the footprint, and the manager and reviewer only report.** The
     `cycle-manager` skill writes nothing. The `pr-reviewer` skill posts one comment. So the merger,
     which writes to the tracker already, is the one that records an approved path on the issue.
- **Context:** #68, from the owner's policy of 2026-10-06. The owner approved this issue's plan
  ("I'm good with all the changes. Let's go ahead."). Before this entry, a PR that changed a file
  outside its issue's footprint always escalated, even when an acceptance criterion needed the file
  and no risk list covered it. The owner then spent a review on that decision. An independent agent
  can make it, bounded as above.

  **Why the merger writes the footprint.** An approved widening must be recorded on the issue, so
  that a later reader sees the file was allowed. The `cycle-manager` skill writes nothing, by its own
  rule. The `pr-reviewer` skill posts one verdict comment and no other write. The merger is the only
  agent that already writes to the tracker on a merge, and it writes the record before the merge.
  A write that fails stops the merge, because a merged diff with no record would contradict the issue.

  **Why the bold report rule.** A widening is a decision taken without the owner's review. Printing
  it in bold in every run report, and on the issue, lets the owner see that a decision was taken, and
  revert it by reverting the PR.

  **Why a removed setting, with a pointer section.** `CLAUDE.md` §6 condition 3 asked whether the
  project enforced footprints. Five skills read an on or off field from `PROJECT.md`, and each one could
  disagree. The owner ruled on 2026-10-06 that footprint checking is not a project setting. The
  `PROJECT.md` section keeps its heading, because `README.md` tells a reader to pin a version, and an
  older installed skill reads "on" from that heading. The body now states the rule, and no skill reads
  the body as a setting.

  **Corrects, not supersedes.** D-15 lists "footprint enforcement on" among its fail-closed defaults.
  That field no longer exists, and D-15 otherwise stays in force, so this entry changes its mechanism
  and not its rule. The relation is `Corrects`.
- **Corrects:** D-15 — the fail-closed default "footprint enforcement on", and the field that carried
