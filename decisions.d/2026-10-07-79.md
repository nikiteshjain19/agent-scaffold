# D-79 — 2026-10-07 — An approved plan reaches `issue-writer` from the working tree, and its text travels in the issue

- **Decision:** Three rules change how an approved plan reaches the `issue-writer` skill.
  1. The `issue-writer` skill stops on a named plan only when the plan file is in neither the
     working tree nor the default branch. It drafts from an approved plan file in the working tree
     on the plan path, with no stop. A draft plan still goes to the user.
  2. A one-unit design presents and stops for approval under `feature-plan` §5, exactly as a plan.
     It writes no plan file and schedules no "Commit this plan" unit. On approval, `issue-writer`
     drafts the unit with Wave "none".
  3. The "Commit this plan" unit's issue carries the whole approved plan file verbatim, `Status`
     line included. The lane writes `docs/plans/<slug>.md` from that quote, byte for byte, and never
     from a working tree. A plan too large for one issue body makes the skill stop and ask. It never
     shortens the plan.
- **Context:** #79, from the review of PR #75. The owner approved filing this follow-up on
  2026-10-06. D-60 item 1 routes the plan through its own "Commit this plan" unit, but the
  `issue-writer` skill's Track B stop ("not on the default branch") fired at every hand-off. The
  plan is never on the default branch when `issue-writer` first reads it, so the stop was a false
  one. A third gap sat in the same hand-off. `issue-loop` cuts each lane's worktree fresh from
  `origin/<default branch>`, and the uncommitted plan file never reaches `origin`. The lane receives
  only the issue, so the issue must carry the plan. The issue already reaches the lane whole, so
  quoting the plan in it adds no new list, field or config.
  **Why the working tree is read.** The planning session holds the approved plan, and the
  `issue-writer` skill runs in that session. Reading the plan there removes the false stop without
  committing the plan from the design session, which `feature-plan` never does (`CLAUDE.md` §3).
  **Why the one-unit exit changes.** D-60 left the one-unit design without an approval gate and
  without a rule for its plan file. This entry gives it the same approval gate as a plan, and it
  writes no plan file, because nothing needs to land through a unit.
- **Corrects:** D-60 — item 1, the plan hand-off to the `issue-writer` skill. D-60 still binds: the
  plan still lands through its own unit. This entry changes the hand-off mechanism and states the
  one-unit case that D-60 left open.
- **Affects:** the `issue-writer` skill (§1 Track B, the "Read the plan file" bullet and its
  sub-bullets); the `feature-plan` skill (§2, "A one-unit design exits here"; §5, its opening
  paragraph, the "plan reaches the default branch" paragraph and its item 2); `decisions.d/2026-10-06-60.md`;
  #79.
