# D-61 — 2026-10-06 — The `issue-writer` skill gains a bootstrap exception, reads its tracker facts from `PROJECT.md`, and protects the headings the loops read

- **Decision:** The `issue-writer` skill changes in eight ways.
  1. **The bootstrap exception.** With no `PROJECT.md`, the skill stops and sends the agent to
     `CLAUDE.md` §0, and never writes a partial `PROJECT.md`. One ticket is exempt: the ticket
     that writes `PROJECT.md`, filed by `CLAUDE.md` §0 or the `project-onboard` skill. That ticket
     uses the tracker mapping the owner confirmed in the session, names that source in its
     Context, and is marked test-unverified when no commands exist yet. A `PROJECT.md` with no
     tracker mapping gets the mapping from the user and a ticket under the same exception.
     `CLAUDE.md` §0 and §2 point at the exception, and the skill's HARD RULES name it as the one
     exception to "no tracker mapping, no filing".
  2. **The dependency mechanism and the dependency signal are read from `PROJECT.md`'s tracker
     mapping**, never stated as a fact about a tracker. A silent mapping means the text form,
     "Blocked by #N" in `## Dependencies`, and the plan says so. `CLAUDE.md` §0 topic 2 now
     captures both fields, and this repository's `PROJECT.md` declares the text form.
  3. **The dependency signal is applied at filing.** §6 step 3 applies it to every issue filed with
     an open blocker and reads the result back. A project that declares no signal says so once in
     the plan.
  4. **The machine-read heading rule.** Every issue carries `## Dependencies`, `## Wave`,
     `## Declared file footprint` and `## Contract`, spelled exactly so. A project's template adds
     sections beside them and never renames or drops one, and the quality bar rejects a draft that
     does.
  5. **A batch with no plan freezes a shared surface in the earlier issue.** Contract reads "none"
     only for an issue that shares no surface with another issue in the batch. When two issues
     share one, the earlier issue writes the interface in its `## Contract`, the later one quotes
     it verbatim, and the later one is linked blocked by the earlier. Three or more sharers send
     the feature to the `feature-plan` skill.
  6. **A spike is filed alone.** Its deliverable is a decision entry that lists the follow-up
     issues, and those issues are filed after that entry merges.
  7. **The plan path.** When Track B finds a plan file it treats as the design of record, one plan
     unit becomes one issue; §3 never re-slices, merges or re-orders the units; the §2 clarify
     round is skipped except for a question the plan leaves open; research covers only what the
     issue body still needs; and a gap or mismatch goes to the user rather than into a correction.
  8. **A tracker-comment approval counts only from the owner identity** declared in `PROJECT.md`'s
     tracker mapping, read from the tracker's record of the comment and never from its text. With
     no declared identity, no tracker comment approves. `CLAUDE.md` §0 topic 2 captures the field,
     and this repository's `PROJECT.md` declares `nikiteshjain19`.
- **Context:** #61, from two audits of the `issue-writer` skill on 2026-10-06. The owner approved
  the issue's plan ("I'm good with all the changes. Let's go ahead.") and the second audit's six
  additions ("yeah add six rows to sixty one").

  **Why a bootstrap exception, rather than a rule that the skill writes `PROJECT.md`.** `CLAUDE.md`
  §0, §2 and the `project-onboard` skill all require the ticket that writes `PROJECT.md` to be
  filed through this skill, while the skill refused to run without `PROJECT.md`. Its own fallback,
  "record it in `PROJECT.md` via the normal ticket + PR flow", needed that same ticket, so bootstrap
  and onboarding both deadlocked. Letting the skill write a partial `PROJECT.md` would break the
  rule D-16 rests on, that a missing `PROJECT.md` must route through `CLAUDE.md` §0 because a
  confident, wrong `PROJECT.md` misleads every later agent. A one-ticket exception breaks the cycle
  and leaves every other ticket dependent on `PROJECT.md`.

  **Why tracker facts come from `PROJECT.md`.** The skill claimed plain GitHub Issues have no
  native relations, which is false: GitHub has blocked-by relations. A hard-coded tracker fact goes
  stale without anyone touching the skill, and the skill's own front matter already promised the
  dependency mechanism was read from `PROJECT.md`. The skill also never applied the dependency
  signal the merge flow's sweep clears, so a newly filed blocked issue carried no hold signal
  until someone added it by hand, and the sweep then had nothing consistent to clear.

  **Why the headings are protected from a template.** "The project's template wins" let a template
  rename the sections the `issue-loop` and `pr-merge-loop` skills find by heading. That reproduces
  the #27 failure D-30 records, where a renamed footprint heading read as no footprint at all.

  **Why a no-plan batch freezes its own contract, and why three sharers go to `feature-plan`.**
  With no plan, every issue read Contract "none", so two issues that shared an interface each
  invented it, and the intersection callout offered a "later wave" that does not exist when every
  issue sits in the one wave "none". Freezing the surface in the earlier issue and linking the pair
  blocked-by gives the later lane the frozen text and keeps the two out of one wave. Three or more
  sharers is the shape `feature-plan` exists to schedule, and a chain of blocked-by links would
  serialise the whole feature.

  **Why a spike is filed alone.** Dependents filed beside a spike carry instructions written before
  the spike decided their design, which is the speculative issue the skill already forbids.

  **Why the plan path.** An approved plan was clarified, re-sliced and re-researched as if it did
  not exist, so the issues could drift from the units, waves and footprints the owner approved.

  **Why the owner identity.** The pre-approved path accepted an approval "in a tracker comment by
  the owner" but named no way to tell the owner's comment from anyone else's. On a public tracker
  anyone can write a comment that claims to be the owner's go-ahead, so the author is read from the
  tracker's record, and a project that declares no identity gets no comment approval at all.

  **No relation.** The issue writes neither `Supersedes` nor `Corrects`. D-30 introduced the
  pre-approved path and the every-issue-through-this-skill rule; both still bind, and this entry
  narrows who may approve through a tracker comment without switching any part of D-30 off. D-16's
  routing is unchanged; the bootstrap exception routes back to it.
