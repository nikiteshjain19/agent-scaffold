# D-36 — 2026-10-05 — The ruleset `main — merge gate` is live, so D-13's record of a waiting window is stale

- **Decision:** The ruleset `main — merge gate` has been active on `main` since the owner applied
  it on 2026-10-04. D-13 states that `PROJECT.md` describes the gate as only honoured until the
  owner applies it. D-13 also states that a window remains before the owner applies it. Neither
  statement is true any longer. D-13's decision is unchanged.
- **Context:** The owner applied the ruleset by hand on 2026-10-04, as D-13 decided. A read-only
  `gh api repos/nikiteshjain19/agent-scaffold/rules/branches/main` call on 2026-10-05 returns the
  four rule types D-13 names: `pull_request`, `required_status_checks`, `non_fast_forward` and
  `deletion`. PR #32 (#29, `1d4b5c9`) then rewrote the **Status** sentence in `PROJECT.md`, "Merge
  gate" → "Enforcement mechanism", to say the ruleset is active on `main`. #29 left D-13 out of
  scope, so D-13's stale sentences survived it. A reader who trusts D-13 alone therefore believes
  `main` is unprotected.

  **Why `Corrects`, not `Supersedes`.** `CLAUDE.md` §7 asks one question: does the earlier decision
  still bind? D-13 does. No agent creates, edits or deletes the ruleset, or any other repository
  setting. No approving review is required. There is no `CODEOWNERS` file and no bypass actor. The
  four rules stand as D-13 lists them. Only a recorded statement of fact went stale when the owner
  acted, which is exactly the case §7 assigns to `Corrects`: the earlier entry stays in force, and
  a reader must read both. D-3 is the precedent. It corrected D-1 and D-21 the same way, for a fact
  that PR #24 made false while their decisions stood.
- **Corrects:** D-13.
- **Affects:** `decisions.d/2026-10-04-13.md` (D-13); `PROJECT.md`, "Merge gate" → "Enforcement
  mechanism" (already correct, no change); #29; PR #32; #36.
