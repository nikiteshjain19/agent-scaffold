# D-66 — 2026-10-06 — The `cycle-manager` skill agrees with the skills it composes: C3, C4 and C8 change, one wave per cycle, a valid digest, and a re-review after a new decision

- **Decision:** The `cycle-manager` skill changes three frozen contracts and six behaviours.
  1. **C3 names the `REPAIR` bounds that apply.** A repairer follows bounds 1 to 9 and 12 of the
     `pr-merge-loop` skill, and its "Leave the record" section. Bounds 10 and 11 belong to a full
     `pr-merge-loop` run, and the repairer does not run them.
  2. **C4 gains the outcome `escalated <bound n>`.** The outcome line reads
     `outcome   <pushed | discarded | refused | escalated <bound n>>`. A repairer writes
     `escalated 3` for a repair that needs a file outside the footprint, `escalated 9` for a check
     that is not green on the new head, and `escalated 1` for a pass whose record failed to post,
     because bound 1 requires a record for every pass.
  3. **C8 predicates 2, 3 and 4 change.** Predicate 2 reads "The count of completed repairs reaches
     the project's cap." A completed repair is one whose C4 block returned `pushed`, so a cap of N
     allows N repairs and a cap of 0 allows none. Predicate 3 reads "The same repairable finding
     survives two consecutive rounds." A repairable finding is a check or condition line that reads
     `fail`, `fired` or `unevaluable`, matches a `REPAIR` shape R1 to R5, and is neither condition 6
     nor a condition on the "Never repair these" list. Two lines are the same finding when both are
     repairable and quote the same evidence. **When the manager cannot tell whether two lines match,
     it counts them as the same finding**, so the loop stops and the pull request reaches the user.
     Predicate 4 reads "A repair returns discarded, refused or escalated."
  4. **A verdict with no repairable finding dispatches no repairer.** DRIVE step 7 stops the loop
     instead, and carries the verdict to the digest. That stop finishes the pull request exactly as
     predicates 2 to 4 do, and the skill names it `no repairable finding` wherever it names a stop
     predicate.
  5. **One wave per cycle.** Each cycle runs the `issue-loop` skill for exactly one wave: its §1
     once, dispatch, no refill, then END OF RUN. The run hands its pull requests to the manager
     after END OF RUN, never one at a time. A wave member the lane budget left undispatched stays
     unclaimed, and a later cycle can select it. The `issue-loop` skill's phase list and its §6
     item 6 state the same rule for a run under the manager.
  6. **The digest presents a valid review.** Before each verdict entry's ASK block, the manager
     prints what the pull request changes in at most three bullets, written from the host's view
     and diff of the pull request, the outcome of the seven pre-merge checks from the verdict's
     `FINDINGS`, and one bottom-line sentence naming what decides the merge. None of that reading
     enters C1, C3 or C5.
  7. **The `issue-loop` skill's questions reach the cycle digest.** The manager holds that run's
     Escalation digest entries beside the cycle record, adds no field to C7, re-prints them
     unchanged as their own group, and counts them. An answer is recorded in the user's own words.
     The manager writes nothing to the tracker, so the issue keeps its input-needed signal until a
     human posts the answer and clears the signal.
  8. **THE BAR names its one exception, and the isolation claim narrows to what holds.** The
     `issue-loop` coordinator's writes — the claim, the lane branches and worktrees, the release of
     a bounced claim, and its configuration stop — are the one named exception to the bar. The
     briefs keep this run's context from a reviewer, and never the author's account: the reviewer
     reads the pull request's title and body from the host, and checks the body against the diff.
     "Never add a field" covers C1, C3 and C5 in both places it is stated.
  9. **A decision entry that postdates a verdict sends the pull request back to a reviewer.** DRIVE
     step 2 records the filenames in `decisions.d/` on the fetched default branch beside each
     verdict. MERGE step 1, and step 3 of "A carried pull request", list the directory again. A
     filename that was absent when the verdict arrived sends the pull request to DRIVE step 1 for a
     fresh review, and an answer given on the old verdict is asked again. The re-review is neither
     a head move nor a round. When the directory cannot be listed, the manager dispatches nothing
     for that pull request and names it in the run report.
- **Context:** #66, from a per-skill audit of the `cycle-manager` skill and a separate design review
  of it, both on 2026-10-06. The owner approved the issue's plan ("I'm good with all the changes.
  Let's go ahead."), asked that the issue absorb the design review's missing findings, and on the
  same day moved #10 items 1, 5 and 8 into it, choosing that the cap counts completed repairs.

  **Why predicate 3 compares only repairable findings.** Every non-approve verdict carried the
  condition 6 line, so the old predicate 3 fired at round 2 on every pull request, and the repair
  cap could never bind. A finding on the never-repairable list repeats by design, because no repair
  may touch it, so it cannot show that a repair failed either. The tie-break counts a doubtful pair
  as the same finding, because that stops the loop and puts the pull request in front of the user,
  which is the fail-closed outcome `CLAUDE.md` §6 requires. The opposite tie-break would spend a
  repair round on a guess.

  **Why the cap counts completed repairs.** The old predicate stopped when the round number reached
  the cap, and the round number starts at 1, so a cap of N allowed N-1 repairs and a cap of 1 behaved
  like 0. The issue offered a ">" comparison instead. Counting repairs that pushed states the cap in
  the unit `PROJECT.md` names, so a reader checks it without knowing where the counter starts.

  **Why a verdict with nothing repairable dispatches no repairer, rather than C4 gaining an
  outcome.** The issue allowed either. A repairer dispatched on a policy flag alone can only return
  "nothing to do", which costs a dispatch per pull request and tells the manager nothing the
  findings did not. The manager already has to read the findings to evaluate predicate 3, so the
  same reading decides whether a repairer has work. The frozen C4 outcome line in the issue's
  Contract carries no "nothing repairable" outcome, which settled it.

  **Why C3 scopes bounds 10 and 11 out rather than the `pr-merge-loop` skill changing them.** Bound
  10 re-runs that run's CLASSIFY, and bound 11 sends the pull request to that run's escalate lane.
  Neither exists inside a dispatched repairer, which has no CLASSIFY and no lane. Under the manager
  the fresh reviewer re-reads the repaired head instead. Those two bounds are correct for the skill
  that owns them, so the contract that cites them narrows the citation.

  **Why one wave per cycle.** The manager's heading said one wave per cycle, while the `issue-loop`
  skill looped to a stall and handed pull requests off as they went green. Both cannot hold. One
  wave per cycle keeps the cycle the unit the run report counts, and lets every pull request of a
  cycle reach one digest. Refilling nothing also means a wave member the lane budget left waiting
  is never claimed, so another session, or the next cycle, can take it.

  **Why the manager sends the pull request to a reviewer after a new decision, rather than raising
  a digest entry.** A digest entry would require the manager to judge which pull requests a decision
  touches. The manager judges no decision, and it cannot write. The reviewer's pre-merge check 2
  already reads every decision entry the default branch gained since the branch point, so a fresh
  review is the one actor that can decide whether the decision invalidates the pull request. The
  re-review is bounded without a counter, because a decision entry reaches the default branch only
  through a merge, and a cycle merges finitely many pull requests.

  **Why the digest gains a summary of the change.** `CLAUDE.md` §6 approval gate rule 3 voids an
  approval given without a presented review. The digest asked for an approval while saying nothing
  of what the pull request changes, so every approval it collected was void.

  **Why the BAR's exception is named, why it is needed, and why it is acceptable.** The old text
  claimed the manager wrote nothing and named only the claim as the coordinator's write, while the
  coordinator also creates lane branches and worktrees and releases bounced claims. Running the
  `issue-loop` skill as a subagent would remove those writes from this context, but it would nest
  every builder under that subagent, which breaks the sibling topology the skill rests on. The
  writes are acceptable because none of them is content that reaches a diff, a brief or a verdict.

  **Why the isolation claim narrows.** The relay rule said no builder narrative reaches a reviewer,
  but the reviewer reads the pull request's title and body from the host, and the builder wrote
  them. What the briefs guarantee is that nothing from this run's conversation reaches a reviewer.
  The `pr-reviewer` skill's own §0 rule governs what it reads on the host, and its pre-merge check 7
  checks the body against the diff, so the manager states the narrower guarantee and vouches for
  nothing it does not check.

  **One stray.** DRIVE step 8 cites predicate 4 and named only `discarded` and `refused`. The issue's
  footprint did not name that step. Leaving it would make step 8 skip an `escalated` outcome
  entirely, so the pull request that makes this change edits that one line and reports it as a
  stray.

  **Relations — the `CLAUDE.md` §7 test applied to D-5 and D-20.** D-5 states "C1, C4, C5, C6, C7
  and C8 are unchanged", and D-20 states "C1 to C7 are unchanged". Each sentence records the scope of
  that entry's own change, at the time it was made. Neither decided that those contracts stay
  frozen, and this entry switches off no rule either one made. D-5's verdict shape, its `FINDINGS`
  block, and its reason for keeping `ADVISORY` out of predicate 3's reach all still bind. D-20's
  fifth predicate, its two merge routes, its carried questions and its closing pass all still bind.
  The decision-log re-review adds a reason to send a pull request back to a reviewer beside D-20's
  moved head, and changes neither D-20's count nor its routes. The log's own precedent agrees: D-20
  changed C8 after D-5 said C8 was unchanged, and wrote no relation to D-5. So this entry writes
  neither `Supersedes` nor `Corrects`, and edits neither file.
