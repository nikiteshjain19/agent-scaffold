# D-63 — 2026-10-06 — The `pr-merge-loop` skill honours its own stops on every merge path, merges with merge commits, and moves four parts into reference files

- **Decision:** The `pr-merge-loop` skill, `PROJECT.md` and `CLAUDE.md` §6 change in twelve ways.
  1. **The go-ahead path has guards.** Before it merges, the escalate lane stops on a required
     check that is not success when re-read, on a ticket that was cancelled, descoped or
     superseded, and on a missing review record for the current head. The ASK BLOCK withholds the
     merge option in those cases. Step a also stops when this run posted a
     `REPAIRED BY THE MERGE LOOP` record, so a body-only repair is covered. Only an answer that
     names the PR, by number or by title, approves it; a bare "go ahead" is asked again, and any
     other answer queues the card's question and moves on.
  2. **Approval gate rule 2 now reads K8:** "An independent reviewer must still return a fresh
     verdict on the resolved head SHA. In the auto tier, that verdict must be approve." The
     escalate lane requires a fresh verdict, of any value, on a resolved head, and shows it on the
     card.
  3. **A BASE move re-asks only when it matters.** A moved head re-presents the card. When only
     BASE moved, the merger intersects `git diff --name-only <BASE at card time> origin/<BASE>`
     with the PR's changed files and re-runs CLASSIFY and CONFLICT. It re-asks only when the
     intersection is non-empty or either result changed.
  4. **Reviewer findings reach REPAIR.** The repairable findings (R1–R5) of a non-approve verdict
     go through the same bounds before the escalate lane.
  5. **The PROBE order question is a hard wait.** The run no longer proceeds on an unanswered
     order.
  6. **Every PR merges with a normal merge commit, never a squash** — the owner's ruling of
     2026-10-06. `PROJECT.md`'s Merge strategy row reads K11, and a branch is kept while another
     open PR is based on it, then deleted. CONFIG needs no stacked-parent exception under a
     merge-commit strategy; under squash or rebase with no declared exception it holds the parent
     and escalates. STACKED PAIRS item 9 deletes a kept branch only when its tip is an ancestor of
     BASE.
  7. **CLASSIFY gate 1 carries the resolution-commit exemption, and names its evidence.** A
     mechanical resolution commit pushed under CONFLICT is not a commit the merger wrote. The
     evidence is this run's push log and a resolution or repair record that names this run; a git
     author or committer field is not evidence of authorship.
  8. **A check still pending after the re-poll is red.** CONFLICT step 6 and REPAIR bound 9 read
     the checks once the push lands, re-poll once when none reported, and escalate under
     escalation condition 2 when a required check is still pending. No timeout field is added.
  9. **The SCHEMA CHECK is read-only.** It uses introspection only, through read-only access the
     project names, and flags drift when the project names none.
  10. **A stacked pair under SINGLE-PR MODE stays held.** The hold names both PRs and says a full
      `pr-merge-loop` run merges the pair, parent first.
  11. **CONFLICT, REPAIR, STACKED PAIRS and the review card's format live in reference files**
      under `plugins/hivion/skills/pr-merge-loop/references/`. Each heading stays in `SKILL.md`
      with a pointer sentence, every step, bound and item keeps its number, and RULES is an index
      plus five hard rules.
  12. **The `MERGE-LOOP REVIEW RECORD` is the `CLAUDE.md` §6 review record** — the owner's ruling
      of 2026-10-06. The `pr-reviewer` skill's verdict comment is the independent verdict that
      record cites, never the record itself.
- **Context:** #63, from two audits of the `pr-merge-loop` skill on 2026-10-06, plus two items moved
  from #10. The owner approved the issue's plan ("I'm good with all the changes. Let's go ahead.")
  and, when a lane found that the K11 row contradicts a "no squash" check, ruled "wording wins".

  **Why the go-ahead path needed guards.** The escalate lane checked only authorship and a stacked
  parent once the user said "go ahead", so a red PR, a PR whose ticket was cancelled, or a PR with
  no review record merged on approval. The skill declares each of those a stop elsewhere, and an
  approval is a decision about the change, not a waiver of the gate's other conditions. Withholding
  the merge option on the card closes the invitation; the guard step closes the path, which is
  where the merge actually happens. A bare "go ahead" named no PR, and `CLAUDE.md` §6 approval rule
  1 requires an approval of that specific PR.

  **Why rule 2 changes, and its origin.** Approval gate rule 2's resolution-commit exemption was
  ratified by the owner on 2026-07-31 (private D-77). Its last sentence demanded a fresh `approve`
  on a resolved head in every tier. A risk-listed PR escalates on a fully green signal, and its
  reviewer correctly returns `escalate`, so a resolved risk-listed PR could never satisfy that
  sentence and could never merge, even with the user's approval. K8 keeps the fresh read of the
  resolved diff in both tiers, and keeps `approve` as the auto tier's bar.

  **Why a BASE move re-asks only when it touched the PR.** Every merge moves BASE, so "re-present
  the card when BASE has moved" voided every queued approval after the first merge of a run. The
  intersection of what BASE gained with what the PR changes, plus a fresh CLASSIFY and CONFLICT,
  is exactly what can change what the PR would land. `CLAUDE.md` §6 approval rule 4 expires an
  approval when the diff changes, and this test reads that change instead of assuming it.

  **Why reviewer findings go to REPAIR.** REPAIR ran only on findings from CLASSIFY, CONFLICT and
  PROBE, so a defect the independent reviewer found (R3, R4) went straight to a human even when the
  merge loop could repair it in the same run. The bounds are unchanged, so the repair still makes
  the merger the author and still hands the PR to a later session.

  **Why the PROBE order question waits.** `CLAUDE.md` §13 asks a question about the run itself in
  place, the run order above all. The old text waited and then proceeded on silence, which is both.
  The second audit asked for a queue instead; that is out of scope because §13 decides it.

  **Why merge commits.** The owner ruled on 2026-10-06 that every PR merges with a normal merge
  commit, never a squash. A squash rewrites the parent's commits into a new one, so a stacked
  child's diff re-includes its parent's changes after the parent merges; a merge commit keeps the
  parent's commits as ancestors of BASE. Under a merge-commit strategy the stacked-parent case
  needs no exception, which also satisfies the `issue-loop` skill's stacked-lane precondition
  (D-64). The ancestor test before deleting a kept branch makes sure no commit pushed after the
  merge is lost. No earlier entry chose squash, so this entry writes no `Supersedes` or `Corrects`;
  D-47's description of a historical squash-sorted changelog stays true.

  **Why gate 1 carries the exemption, and why a git identity is not evidence.** CONFLICT step 8
  re-runs CLASSIFY after a resolution, and gate 1 asked only "did you write any commit", so every
  resolved PR escalated on authorship even though the exemption was stated in CONFLICT and in
  escalate-lane step a. A builder, a repairer and a merger often push under one git identity, so
  the author and committer fields cannot separate them; only this run's push log and the records
  the loop posts can. The residual risk, a commit an earlier session wrote under the same identity
  with no record, is named in the gate. A session-id trailer would close it, and is out of scope
  because no commit here carries one.

  **Why a pending check after the re-poll is red, and why no timeout field.** CONFLICT step 6 and
  REPAIR bound 9 waited for checks on a new head with no limit, so a stuck check stalled the whole
  run. Escalation condition 2 already counts a pending check as red, and the go-ahead guard
  re-reads the checks before any merge, so a timeout field in `PROJECT.md` would add a second
  number for a rule that already exists.

  **Why the SCHEMA CHECK is read-only.** It said to "query the actual DB" with no limit on what a
  query may do. A write to a live database is an effect a revert cannot undo. Introspection
  through read-only access answers the drift question, and naming no such access makes the check
  unevaluable, which `CLAUDE.md` §6's tie-break reads as met.

  **Why a stacked pair in SINGLE-PR MODE stays held.** Merging the parent requires retargeting the
  child, and that retarget writes to another PR, which this mode never does. The child's verdict
  would also predate its new base, and the `cycle-manager` skill's C2 verdict block has no base
  field that could show it. So the mode holds both PRs, names them, and leaves the pair to a full
  `pr-merge-loop` run, which merges the parent first.

  **Why the reference-file split.** The skill had grown to 1,801 lines, with RULES restating most
  sections above it. Each `cycle-manager` merger loads the whole file once per PR, and each
  restatement is a place for a rule to drift; gate 1's missing exemption was one. CONFLICT, REPAIR,
  STACKED PAIRS and the card format are each read only when their trigger fires. Their headings stay
  in `SKILL.md` because `CLAUDE.md` and the `cycle-manager` skill cite them by name, and their
  numbers stay because REPAIR bounds and STACKED PAIRS items are cited by number. The
  `issue-loop` skill's stacked lane made the same move (D-64).

  **Why the merge loop's record is the §6 record.** Both skills claimed their comment was the
  `CLAUDE.md` §6 review record, and §6 allows one comment, posted by the agent that ran the review.
  The owner ruled that the merge loop's record is that comment and that it cites the reviewer's
  verdict. D-62 wrote the `pr-reviewer` half; this entry writes the `pr-merge-loop` half.

  **No relation.** No earlier entry chose squash or set the go-ahead path's checks. D-7's relayed
  answer checks, D-20's merge routes and D-62's freshness rule all still bind, and this change
  applies them. This entry writes neither `Supersedes` nor `Corrects`.
