# D-67 — 2026-10-06 — The `project-onboard` skill writes a `PROJECT.md` the other skills can run on, and keeps secret locations in the session

- **Decision:** The `project-onboard` skill changes in eight ways.
  1. **New fail-closed defaults.** An unresolved merge strategy makes the merge flow stop and ask
     before every merge. An unresolved target state after merge changes no ticket state, and the
     run reports it. An unresolved stacked-parent merge-commit exception is "none", so stacked lanes
     stay off. The generated `PROJECT.md` also gains slots for the base branch, the branch naming
     convention, the merge strategy, the tracker scope, the target state, the merge-comment policy,
     the auto-link convention, the label vocabulary, the assignee convention, the dependency
     mechanism, the command that reads the green signal and the command that resolves changed files
     against the risk list. The survey proves the default branch and the allowed merge methods with
     host API commands.
  2. **The hold-signal writes happen after the adoption pull request merges.** WRITE step 5 declares
     the pre-adoption signal in `PROJECT.md` and makes no tracker write. The pull request body lists
     applying the signal, and reading back every result, as a post-merge step. A human, or an agent
     with the owner's go-ahead for that issue, clears the signal after rewriting the issue body to
     the `issue-writer` skill's anatomy.
  3. **The adoption ticket is filed under the `issue-writer` skill's bootstrap exception** (D-61),
     with the tracker mapping the owner confirmed in RECONCILE.
  4. **The codebase survey permits only read-only introspection.** The `project-audit` brief files
     no ticket, returns its action plan as a list, runs only the read-only introspection that skill
     defines with credentials already present, and never requests a credential. The survey rule
     becomes "Change no production system". The isolated surveyor receives the tracker's identity
     and access route from the interview, and nothing else.
  5. **Secret locations stay in the session, and the survey requires a scanner.** A location is
     named only in this session's report. The adoption ticket, the pull request and `PROJECT.md`
     carry a count, the date it was reported and whether rotation is pending, and a HARD RULE
     forbids a location on any durable surface. 2.3 requires a secret scanner with its redaction
     option on, run against the working tree and the full history. With no scanner installed it
     records "secrets: not surveyed" and installs nothing.
  6. **The test suite runs only after a configuration read, and only in a credential-free
     environment.** The survey reads the runner's configuration, its environment files and its CI
     job first. A non-local host or a credential read means "not run", with the file and line. A run
     happens once, in a scratch worktree, in the environment #62 defines, and a credential failure
     there is never retried outside it.
  7. **The workflow file keeps its path and its section numbers.** The workflow file is defined as
     the `CLAUDE.md` text that holds the §0 "Project Bootstrap" section, wherever the session loaded
     it from. When it joins an existing agent instruction file, the owner's content moves into a
     separate linked file or after the workflow file's last numbered section.
  8. **The observe-mode exit is defined by commands.** A false green is a merge to the default branch
     whose required checks passed and that a later commit in the period reverts. An unexplained red
     is a CI run on the default branch that failed, then passed on a re-run at the same commit.
     Hotfixes are not counted.
- **Context:** #67, from two audits of the `project-onboard` skill on 2026-10-06. The owner approved
  the issue's plan ("I'm good with all the changes. Let's go ahead.") and the second audit's items
  ("yes update 67 with the six items plus the scanner option").

  **Why the defaults and slots.** The generated `PROJECT.md` had no slot for the fields the
  `pr-merge-loop` skill resolves in its CONFIG — the base branch, the merge strategy, the target
  state, the merge-comment policy — and no default for any of them. The merge flow would then
  improvise exactly the values it acts on when it merges and closes tickets, which a revert cannot
  undo. A default that stops and asks costs one question per merge; an improvised strategy costs a
  wrong merge.

  **Why the hold-signal writes wait for the merge.** Applying the signal before the adoption pull
  request merges marks the backlog with a label no merged `PROJECT.md` declares yet, and if the pull
  request is rejected the label is left behind with no rule to explain it. Nothing ever cleared the
  signal either, so the held backlog would have stayed invisible to the loop forever; naming the
  clearer closes that.

  **Why the bootstrap exception.** The skill filed the adoption ticket through the `issue-writer`
  skill before any `PROJECT.md` existed, and that skill refused to run without one. D-61 added the
  exception on the `issue-writer` side; this entry aligns the onboarding side.

  **Why only introspection, and why the surveyor gets the tracker.** Run as briefed, the
  `project-audit` skill filed tickets and queried production, which the read-only survey forbids.
  The isolated surveyor could not find the tracker it had to survey. The tracker's identity and
  access route are an address, not a claim, so passing them does not prime the surveyor the way the
  interview record would.

  **Why secret locations stay in the session, and why a scanner.** Until rotation, a location is a
  map to a live credential, and the adoption ticket and `PROJECT.md` are durable and often widely
  readable. An improvised search pattern differed on every run, so a run that found nothing proved
  little. A scanner's rule set is maintained as credential formats change, and its redaction option
  keeps the value off the screen.

  **Why the configuration read before the test run.** The old rule skipped the suite when it needed
  a live service or a credential, but only a run could show that, and the shell may hold host tokens
  and production variables meanwhile. Reading the configuration first settles most cases without a
  run, and the credential-free environment catches the rest.

  **Why the path-and-numbering constraint.** Every skill cites the workflow file by `§N`. A merge
  with an existing instruction file that renumbers its sections silently breaks those citations. The
  constraint can retire once #18 removes the `§N` citations.

  **Why the exit definitions.** "No false green and no unexplained red" defined neither term, so
  observe mode either never ended or ended on a feeling. Hotfixes are left out because no command
  can tell a hotfix from ordinary work.

  **Why `Corrects`, not `Supersedes`.** D-15's skill, its phases, its adoption rules and its table
  of fail-closed defaults all still bind. This entry changes the mechanism of several of them — how
  the backlog is held, how secrets are reported, how the survey is briefed — and adds rows to the
  defaults table, without switching any part of D-15 off.
