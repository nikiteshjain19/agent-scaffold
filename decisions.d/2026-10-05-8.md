# D-8 — 2026-10-05 — Four `CLAUDE.md` contradictions resolved, each in one direction

- **Decision:** Four places where `CLAUDE.md` contradicted itself, or contradicted a skill, are
  resolved in one direction each.
  1. **Golden rule 3 names both merge tiers.** §1 rule 3 and §0 topic 3 now say an escalated PR
     merges only after the user approves that specific PR, and a PR that trips no escalation
     condition may merge without asking once an independent reviewer approves it. No agent ever
     merges a PR it authored. §6's "Opening a PR" bullet and the `issue-loop` skill's hard rules
     now point at the two-tier gate instead of "the approval gate".
  2. **§4.2 carries the stacked-lane exception by reference.** A child lane the `issue-loop` skill
     dispatches beside its parent, under that skill's §1 step 5, may start while the parent is
     open. §4.2 restates none of those conditions.
  3. **Pre-merge check 4 merges the default branch in, and never rebases a pushed branch.** It now
     resolves only a mechanical conflict, citing approval gate rule 6. Check 3's "close or rebase
     this one" becomes "close or rework this one". §11 rule 9 re-runs the gate after every sync,
     and defines a sync as a rebase before the first push or a merge after it.
  4. **The ASK block gains an optional "Already tried" line.** The `pr-merge-loop` skill's ASK
     BLOCK prints it as its second part, one line long, only when the run already acted on the
     item. A block without it says the run tried nothing. §13 item 3 reads "What you already
     tried, if anything".
- **Context:** #8, from an audit on 2026-09-18. Each item was a place where an agent following one
  passage broke another. All four were still present on `main` at `d729bb9`.

  **Item 1 — why the short version moves, not the tiers.** The auto-merge tier is the newer and the
  more detailed rule, and the skills (`pr-merge-loop`, `pr-reviewer`, `cycle-manager`) implement
  it. Narrowing §6 to match rule 3 would have removed a tier three skills build against. So rule 3
  is rewritten to summarise §6, which is what a golden rule is for. The two rules that never relax
  — no agent merges its own PR, and none merges to resolve uncertainty — stay in force. The first
  stays in rule 3 itself. This repository's own `PROJECT.md` still sends nearly every PR to a
  human, because its risk list covers nearly every path; that is unchanged.

  **Item 2 — why an exception in `CLAUDE.md`, not a removal from the skill.** The issue asked for
  the exception by reference. The stacked lane is opt-in, one level deep, and bounded by six
  conditions in the `issue-loop` skill. Copying them into §4.2 would create a second copy that
  drifts. §4.2 therefore names the lane and cites its conditions.

  **Item 3 — why merge, never rebase.** The issue fixed the direction: make check 4 say what the
  skills enforce. A rebase of a pushed branch needs a force-push. That rewrites the commits a
  reviewer already read, and on a shared branch it discards work another session may hold. The
  `pr-merge-loop` skill's CONFLICT phase and the `issue-loop` skill's §4 step 7 both already forbid
  it. Approval gate rule 6 already said check 4 "tells a reviewer to merge the default branch in",
  which was false until now. Check 4 now cites rule 6 for the mechanical-only bound, so the
  `pr-merge-loop` skill's sentence that its CONFLICT phase "adds the boundary that check lacks" now
  reads "defines the boundary that check cites". Check 3's "rebase" was the same instruction in a
  second place, so it changed too. §11 rule 9 said "after any rebase or merge … during pre-merge
  review". The `issue-loop` skill cites that rule for a lane's own pre-push sync, which is not
  pre-merge review, so the rule now covers every sync. Two passages still name a rebase as a
  trigger: the body-freshness bullet and approval gate rule 4. They were left alone, because each
  says what to do after a rebase happens and neither tells anyone to rebase.

  **Item 4 — why widen the block, and why the line is optional.** Dropping the field was the
  alternative. It was rejected because the DIGEST re-prints only the ASK block, so anything the run
  tried, kept above the block, never reaches the digest, and the user may then suggest the thing
  that already failed. That return trip is the cost §13 exists to prevent. The owner asked for
  short, plain digests. A mandatory line would add "Already tried: nothing" to every merge
  approval, which is noise. So the line appears only when the run acted on the item, and its
  absence is defined to mean the run tried nothing. That way a reader can still tell an omission
  from an oversight. The only worked block in the skill where something was tried, the repair
  hand-off, now carries the line.
- **Affects:** `CLAUDE.md` §0 topic 3, §1 rule 3, §4 step 2, §6 ("Opening a PR", pre-merge checks 3
  and 4), §11 rule 9, §13; the `pr-merge-loop` skill (ASK BLOCK, CONFLICT's "RESOLVE" rationale,
  the REPAIR hand-off block, RULES); the `issue-loop` skill (§7 hard rules); `PROJECT.md`, whose
  "Who merges" row and pre-PR gate line this change leaves for a follow-up (see #8's PR); #8.
